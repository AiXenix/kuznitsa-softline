# «Кузница Softline» — спецификация v0.1

Умный поиск и поисковая аналитика для интернет‑магазина программного обеспечения для юрлиц.
Владелец: **AiXenix**. Этот документ — источник истины для реализации. Общий контекст и жёсткие правила — в `design/BRIEF.md`.
Если спецификация и код расходятся, правим то, что неверно, и фиксируем решение здесь (раздел 23).

Обозначения приоритета: **P0** — без этого демо не состоится; **P1** — сильно усиливает; **P2** — если останется время.

---

## 0. Принципы

1. **Понимание раньше поиска.** Сначала разбираем, *что* человек хочет (сценарий, сущности, ограничения), и только потом ищем.
   Поиск по строке — лишь один из инструментов.
2. **Знание мира ПО не зависит от каталога.** База знаний (`kb/`) знает вендоров, семейства, жаргон, аналоги, роли, задачи.
   Поэтому поиск узнаёт и то, чего в каталоге нет, — это основа блока «чего не хватает в каталоге».
3. **Работает без сети и без платных моделей.** Режим `fast` (правила + словари + локальные эмбеддинги) обязан давать хорошую
   выдачу сам. Режим `smart` добавляет закрытые классификаторы Jev (категоризатор) и реранк. Отказ внешнего API не ломает ответ.
4. **Каждый шаг объясним.** Любой ответ несёт трассу «что агент сделал с запросом» и стоимость. Это прямое требование жюри.
5. **Бизнес‑сигналы не портят релевантность.** Популярность и маржа работают только внутри полосы релевантности.
6. **Выдача для покупателя + вывод для бизнеса.** Каждый поиск пишется в журнал; из журнала агент делает выводы и предлагает
   действия пяти ролям; применённое действие сразу меняет поиск (замкнутый контур).
7. **Данные подменяемы.** 26 ноября придут каталог, запросы и «метрика» организаторов в неизвестном формате.
   Движок работает только с каноническим форматом; всё чужое приводится адаптерами с редактируемым сопоставлением полей.
8. **Детерминизм.** Генераторы mock‑данных — с фиксированным зерном. Ответы LLM кэшируются. Тесты не ходят в сеть.

## 3. Модель данных (канонический формат)

Три уровня: **вендор → семейство (продуктовая линейка, с редакциями) → предложение (SKU‑лицензия)**.
Единица выдачи — **карточка** = семейство × редакция (если редакций нет — семейство). Внутри карточки — варианты‑предложения.

### 3.1. Предложение (`Offer`) — строка `var/data/catalog.jsonl`

| Поле | Тип | Смысл |
|---|---|---|
| `offer_id` | str | уникальный id строки каталога |
| `sku` | str? | артикул вендора (part number) |
| `name` | str | полное название SKU |
| `vendor`, `vendor_id` | str? | название как в каталоге; id из `kb/vendors.yaml`, если сопоставлен |
| `family_id`, `family_name` | str? | id семейства из KB либо производный `auto:<slug>` |
| `edition`, `version` | str? | редакция (id из KB или текст), версия |
| `category_path` | [str] | путь категории как в каталоге |
| `category_id` | str? | id из `kb/categories.yaml` |
| `description` | str | описание |
| `attrs` | {str:str} | сырые характеристики как в источнике |
| `kind` | `license\|service\|course\|hardware\|other` | вид товара |
| `lic.action` | `new\|renewal\|upgrade\|crossgrade\|addon\|support`? | действие с лицензией |
| `lic.model` | `subscription\|perpetual`? | модель |
| `lic.term_months` | int? | срок; для бессрочной — null и `model=perpetual` |
| `lic.metric` | закрытый список из `kb/SCHEMA.md`? | что лицензируется |
| `lic.qty_min`, `lic.qty_max` | int? | диапазон количества (цена за единицу в диапазоне) |
| `lic.pack` | int? | пакет на N (цена за пакет) |
| `lic.audience` | `business\|gov\|edu\|home\|nonprofit\|med`? | для кого редакция |
| `platforms` | [str] | платформы |
| `delivery` | `esd\|box\|paper\|media\|service`? | поставка |
| `language` | `ru\|en\|multi`? | язык |
| `registry` | bool? | в реестре российского ПО (null — неизвестно) |
| `certs` | [`fstec\|fsb\|mo`] | сертификаты |
| `price` | float? | цена за единицу (или за пакет), руб. с НДС как на витрине |
| `price_on_request` | bool | «цена по запросу» |
| `vat` | int? | ставка НДС, 0 — не облагается |
| `available` | bool | можно купить сейчас |
| `popularity` | float 0..1 | популярность (из продаж/просмотров; см. 12.3) |
| `margin` | float 0..1 | доля маржи |
| `sales_90d`, `views_90d` | int | счётчики, если есть |
| `url`, `image` | str? | ссылки |

Любое поле, кроме `offer_id` и `name`, может отсутствовать: чужой каталог бывает плоским. Тогда поля восстанавливаются
разбором названия (раздел 6.2) и обогащением по KB; что не восстановилось — остаётся пустым и не участвует в фильтрах.

### 3.2. Карточка (`Card`)

`card_id` = `family_id` либо `family_id:edition`. Поля: `title`, `vendor_id`, `vendor_name`, `category_id`, `summary`, `kb` (ссылка
на запись семейства в KB, если есть: аналоги, роли, задачи, совместимость, реестр, сертификаты), `offer_ids`, агрегаты
(`price_from`, набор действий/сроков/диапазонов/аудиторий/платформ, `popularity` = максимум по предложениям, `available`),
`origin` (`russian|foreign`), `market_status`. Карточка без предложений не создаётся; KB‑семейства с `catalog: no` живут только
в лексиконе и в блоке «нет в каталоге».

### 3.3. Клиент (`Client`) — `var/data/clients.jsonl`

`client_id`, `title`, `segment` (`smb|mid|enterprise|gov|edu|individual`), `industry`, `size_seats`, `fleet` (`os` — список платформ,
`servers`), `region`, `owned` — список `{family_id, edition, qty, metric, purchased_at, expires_at, offer_id}`, `orders` — список
`{order_id, date, items:[{offer_id, qty, price}]}`. Даты в mock‑данных хранятся **смещениями в днях от момента загрузки**
(`expires_in_days`, `purchased_days_ago`) и материализуются при старте — чтобы «истекает через 21 день» не протухало.
Демо‑профили (подмножество клиентов, `demo: true`): `guest`, `smb_trade`, `gov_clinic`, `edu_university`, `ent_factory`,
`it_company`, `design_bureau`, `accounting_firm` (точное описание — `mock/spec/profiles.yaml`, когда появится).

## 5. База знаний и лексикон

Формат файлов — `kb/SCHEMA.md`. Загрузчик (`kb/loader.py`) **терпим**: читает то, что есть; запись с ошибкой пропускает и
кладёт в отчёт (`KBReport`: счётчики, ошибки, висячие ссылки); отсутствие файла — не ошибка. Внимание: PyYAML читает `yes`/`no`
как булевы значения — поля `registry` (`yes|no|partial`) и `catalog` (`yes|no`) приводить к строкам/булевым единообразно;
одиночное значение там, где ожидается список (`certs: fstec`), считать списком из одного элемента; неизвестные ключи сохранять.
«Платформа» в понимании запроса и в фильтрах — объединение `platforms` и `compat_ru_os` (`astra`, `alt`, `redos`, `rosa`,
`msvsphere` подразумевают `linux`). `python -m kuznitsa.cli kb-check`
печатает отчёт и возвращает ненулевой код только при синтаксически битом YAML. Для модульных тестов — собственная
маленькая база `tests/fixtures/kb_mini/` (не зависит от настоящей, которая ещё пишется).

**Лексикон** (`kb/lexicon.py`) — единый словарь «фраза → сущность», собирается из KB и из самого каталога:

- типы сущностей: `vendor`, `family`, `edition`, `category`, `role`, `industry`, `use_case`, `compliance`, `platform`, `action`,
  `model`, `metric`, `audience`, `delivery`, `deployment`, `faq`, `attr`;
- источники: названия и `aliases` из KB, `kb/slang.yaml` (жаргон, сокращения, транслит, типовые опечатки), названия вендоров,
  семейств и категорий из каталога (на случай каталога без KB), встроенные словари действий, метрик, сроков, платформ;
- ключ — кортеж нормализованных токенов (кириллица лемматизируется pymorphy3, латиница — в нижний регистр);
  сопоставление — самая длинная фраза (до 6 токенов) слева направо; у записи есть `prior` и флаг `strict`
  (короткие и двусмысленные сокращения вроде «бп», «ут», «кес» совпадают только целым токеном и без исправления опечаток);
- двусмысленность сохраняется: одна фраза может вести к нескольким сущностям («офис», «астра», «контур», «компас») —
  решает контекст (раздел 8.6), а если не решил — сценарий `broad` с уточнением;
- одобренные синонимы из админки (таблица `rules`, вид `synonym`) подмешиваются в лексикон без перезапуска.

## 6. Загрузка каталога

### 6.1. Адаптеры

`python -m kuznitsa.cli ingest <файл> [--mapping mapping.yaml] [--dry-run]` принимает CSV/TSV, XLSX, JSON/JSONL, YML (Яндекс‑Маркет).
Шаги: определить формат и кодировку → предложить сопоставление колонок с каноническими полями (по названиям колонок и
содержимому; сохранить в `var/data/mapping.yaml`, его можно править руками) → построчно привести к `Offer` → разбор названия →
обогащение по KB → отчёт качества (сколько строк, доля распознанных вендоров/семейств/категорий, пустые цены, дубли артикулов,
примеры нераспознанного) → записать `catalog.jsonl`. То же доступно из админки (`POST /api/admin/ingest`). Аналогичные адаптеры —
для журнала запросов и выгрузок «метрики» (раздел 14.5). **P0** — CSV/XLSX/JSON; **P1** — YML и загрузка из админки.

### 6.2. Разбор названия SKU (`ingest/nameparse.py`)

Из строки вроде «Kaspersky Endpoint Security для бизнеса – Расширенный Russian Edition. 50‑99 Node 1 year Renewal License» или
«Microsoft Windows 11 Pro 64‑bit Russian 1pk DSP OEI DVD (FQC‑10547)» извлечь: вендора, ядро названия (семейство), редакцию,
версию, действие (продление/renewal/rnw, базовая/новая/base, апгрейд/upgrade, кросс‑грейд/миграция, расширение/add‑on,
техподдержка/support), срок (1 год, 12 мес., 2Y, бессрочная/perpetual), диапазон или количество (50‑99, от 10 до 14, 25+, 5 ПК,
Band K…T), метрику (Node/узел/ПК/устройство, User/пользователь, Server, Core/ядро, ВМ, почтовый ящик), аудиторию (для
образовательных/EDU/Academic, для госучреждений/GOV, для дома), поставку (ESD/электронная, BOX/коробка, OEM/DSP, бумажная),
язык, платформу, артикул в скобках. Правила — таблицами (регулярные выражения + словари), на каждое правило — тесты с примерами
из `/home/bb/kuznitsa-softline-ref/softline/`. Результат каждого поля несёт `source` (`column|name|kb|default`).

Группировка в семейства для чужого каталога: сначала сопоставление ядра названия с `aliases` семейств KB (RapidFuzz
`token_set_ratio` ≥ 90 и совпавший вендор) → id из KB; иначе `auto:<slug(вендор + ядро)>`. Если ядро выделить не удалось —
каждое SKU становится отдельной карточкой.

### 6.3. Обогащение

Для карточек с KB‑семейством переносятся: категория, аналоги, роли, задачи, совместимость, реестр, сертификаты, краткое описание.
Для остальных категория определяется по пути категории каталога (сопоставление с `kb/categories.yaml`), а в режиме с LLM —
пакетно категоризатором Jev (офлайн‑шаг `enrich --llm`, результат кэшируется в `var/data/enrich_cache.jsonl`).

## 7. Индексы (`index/`)

Строятся при старте (или `cli build-index`) и кэшируются в `var/cache` по хэшу каталога и KB.

- `store.Catalog`: предложения, карточки, обратные индексы `sku → offer`, `family → cards`, `vendor → cards`, `category → cards`.
  Артикул нормализуется: верхний регистр, без пробелов, дефисов, точек и слэшей; ищем и точное, и «без хвоста региона».
- **BM25F** по карточкам, поля с весами: `title` 3.0, `aliases` 3.0, `vendor` 2.0, `category` 1.5, `keywords`
  (задачи, роли, форматы из KB) 1.5, `summary` 1.0, `offer_names` 0.7. Своя реализация на разреженных матрицах.
- **Символьные n‑граммы** (TF‑IDF `char_wb` 3–5) по `title + aliases + vendor` — устойчивость к опечаткам и слитному написанию.
- **Эмбеддинги** карточек: текст «название. вендор. категория. краткое описание. задачи» → нормированные векторы, поиск
  скалярным произведением. Отдельно векторы записей KB (задачи, роли, отрасли, категории, вопросы FAQ) — для сопоставления
  смысла запроса со знаниями без LLM.
- Фильтры — булевы маски numpy по полям предложений и карточек.

Целевой размер: до 300 тыс. предложений и 30 тыс. карточек в памяти; всё перебором, без внешних поисковых серверов.

## 8. Понимание запроса (`understand/`)

Результат — `Understanding`: `raw`, `norm`, `tokens`, `corrected`, `corrections[]`, `entities[]` (`type, id, text, span, source, conf`),

### 8.1. Нормализация

NFKC, нижний регистр, «ё→е», унификация кавычек и тире, схлопывание пробелов. Токенизация, **знающая ПО**: `c++`, `c#`, `.net`,
`1с`/`1c` (кириллическая и латинская «с» — одно и то же), `1с:бухгалтерия 8.3`, `office 365`/`o365`/`m365`, `win11` → `windows 11`,
`office2021` → `office 2021`, `sql server 2022`, версии (`8.3`, `v12`, `2024`, `se 1.8`) и артикулы (`KL4867RAKFR`, `FQC-10572`,
`T5D-03341`) не режутся и не исправляются. Кириллические двойники латинских букв внутри латинских слов (и наоборот) выравниваются
(`КL4867RАКFR`, `FQС-10572` из PDF и Word — частый случай); слипшиеся «число+единица» и «бренд+версия» расклеиваются
(`50пк` → `50 пк`, `1сбухгалтерия` → `1с бухгалтерия`). Всё это делается **до** поиска артикула и до словарей.

### 8.2. Точный артикул

Если токен (или весь запрос) после нормализации совпал с известным артикулом — сценарий `sku`, остальные шаги понимания
нужны только для трассы. Токен, *похожий* на артикул (буквы + цифры, длина ≥ 6), но не найденный, — сценарий `sku` с пустым
результатом и причиной `sku_not_found`: ближайшие по расстоянию артикулы + попытка понять остальной текст.

### 8.3. Языковой ремонт (`repair.py`)

Порядок: (1) неверная раскладка в обе стороны (`rfcgthcrbq` → «касперский», `цштвщцы` → `windows`) — применяется, если после
перекладки доля токенов, найденных в словаре, выросла; (2) транслит («майкрософт», «виндовс», «автокад», «фотошоп», «эксель») —
сперва `aliases`/`slang`, затем общий транслит + RapidFuzz по латинскому словарю вендоров и семейств (порог 85);
(3) опечатки по словарю (лексикон + слова каталога): Дамерау‑Левенштейн, порог по длине (до 4 символов — не исправляем, 5–7 — 1,
от 8 — 2), при равенстве — по частоте, при почти равных кандидатах — не исправляем; (4) слитное и раздельное написание
(«мойофис» ↔ «мой офис», «кибербэкап»). Версии, артикулы, числа и `strict`‑сокращения не трогаем. Каждое исправление —
в `corrections` с видом `layout|translit|typo|split|slang|abbr`. Если уверенность средняя — выдача строится по исправленному
запросу, а в ответе есть `did_you_mean` и ссылка «искать как было».

### 8.4. Сущности и параметры (`entities.py`)

- Лексикон (раздел 5) → вендор, семейство, редакция, категория, роль, отрасль, задача, требование регуляторики.
- Количество и метрика: «на 30 компов», «50 пк», «x10», «10 шт», «25 пользователей», «100 узлов», «5 лицензий», «от 50 до 99»,
  «50‑99», числительные словами до ста. Единицы → метрика (комп/пк/арм/узел/устройство/рабочее место → `device`;
  пользователь/юзер/сотрудник/человек → `user`; сервер → `server`; ядро/core → `core`; процессор/сокет → `cpu`; вм → `vm`; ящик → `mailbox`).
- Срок: «на год», «годовая», «1 год», «на 2 года», «24 мес», «3 года», «бессрочная/вечная/perpetual», «подписка».
- Действие: продление/продлить/пролонгация/renewal; новая/базовая/купить; докупить/расширение/дополнительные; апгрейд/обновление
  версии/upgrade; переход с X на Y/миграция/crossgrade; техподдержка/support.
- Цена: «до 5000», «до 5 тыс», «дешевле 10к», «от 1000 до 3000 руб», «недорогой/бюджетный/дешёвый» (сортировка + нижняя ценовая
  треть категории), «бесплатный/free/триал».
- Платформа и совместимость: «для линукс», «под astra», «на мак», «для android», «совместим с 1с».
- Аудитория: «для школы/вуза/образовательная», «для госучреждения», «для дома», «для некоммерческой».
- Регуляторика: «из реестра», «отечественный», «российский», «импортозамещение», «сертификат фстэк/фсб», «для гис/кии/испдн»,
  «152‑фз», «187‑фз», «44‑фз».
- Поставка и развёртывание: «электронная», «коробка», «облако/saas», «on‑premise/локально».
- Исключения: «не X», «кроме X», «без X», «только не X», «не подписка» → `exclude`.
- Версия привязывается к ближайшему слева семейству («windows 11 pro», «astra linux 1.8», «autocad 2024»).

### 8.5. Сценарий (`intent.py` + `classify.py`)

Закрытый список сценариев: `sku, product, vendor, category, task, role_kit, industry, analog, compliance, renewal, license_ops,
spec_list, compare, question, broad, out_of_catalog, off_topic, account, service, promo`. Цена, совместимость, количество,
исключения — модификаторы любого сценария, а не отдельные сценарии.

Сначала правила (в этом порядке, первое уверенное срабатывание побеждает):

1. `spec_list` — две и более строк (или позиции через «;»), в большинстве которых есть продукт и/или количество; вставка таблицы.
2. `sku` — раздел 8.2.
3. `compare` — «vs», «или» между двумя распознанными продуктами/вендорами, «сравнить», «чем отличается», «разница», «что лучше».
4. `question` — вопросительные слова («как», «что такое», «зачем», «можно ли», «нужно ли», «почему», «где взять») или «?» и
   нет явного товарного намерения. «Сколько стоит X» — это `product`.
5. `analog` — «аналог», «замена», «заменить», «вместо», «альтернатива», «импортозамещение X», «российский/отечественный X».
6. `renewal` — «продл…», «пролонг…», «renewal»; `license_ops` — «докупить», «расширение», «апгрейд», «переход с … на …», «миграция».
7. `account` — «мои лицензии», «мой заказ», «счёт», «закрывающие документы», «ключ не пришёл», «личный кабинет».
8. `service` — «внедрение», «настройка», «установка», «техподдержка», «обучение», «курс» (+ продукт или категория).
9. `promo` — «акция», «скидка», «распродажа», «промокод».
10. `role_kit` — сущность‑роль + маркер комплекта («рабочее место», «для бухгалтера», «набор», «комплект», «что нужно», «под ключ»,
    «новый сотрудник», «новый офис на N человек»); `industry` — сущность‑отрасль + такой же маркер.
11. `compliance` — доминирует требование регуляторики (с категорией или без).
12. `product` — распознано семейство (или редакция); если у семейства в каталоге нет ни одного предложения либо в KB `catalog: no`
    или `market_status: left` — `out_of_catalog`.
13. `vendor` — распознан только вендор. 14. `category` — распознана категория. 15. `task` — распознана задача (`use_case`).
16. `broad` — один общий или двусмысленный токен («программа», «лицензия», «софт», «офис», «астра»).
17. Иначе — не определён.

У `off_topic` есть подвид (`understood.subtype`): `hardware` (ноутбук, принтер, картридж — «железо» не наш профиль; но токены,
смарт‑карты и программно‑аппаратные комплексы защиты — наш), `piracy` («кряк», «активатор», «ключ бесплатно», «торрент» —
вежливо объясняем и предлагаем легальные варианты: пробные версии, недорогие и бесплатные аналоги), `gibberish`, `other`.
У `out_of_catalog` — причина: `vendor_left` (вендор ушёл из России), `restricted` (поставки ограничены), `gap` (продукт существует,
но в магазине его нет), `unknown` (похоже на название продукта, которого мы не знаем). В отчёт «чего не хватает в каталоге»
попадают только `gap`, `restricted`, `unknown`; мусор, пиратские запросы и «железо» туда не попадают.

Особые коды в запросе (P2): номер записи реестра российского ПО, коды ОКПД2/КТРУ из закупочной документации — распознаём по
шаблону и, если сопоставить не с чем, честно отвечаем, что по коду показываем подходящую категорию. Формат файла («чем открыть
dwg», «редактор pdf») — сущность `format` из поля `formats` семейств, сценарий `task`.

Категоризатор Jev вызывается, когда правила не уверены (сценарий не определён, сработали конкурирующие правила, остался
значимый `residual`), и всегда — чтобы определить категорию, роль, отрасль и задачу для свободного текста. Один запрос Decisions
с несколькими вопросами: `intent` (20 вариантов с короткими определениями), `category_top` (верхние группы + «другое»), `role`,
`industry`; при необходимости второй запрос: `category_leaf` (листья выбранной группы), `use_case` (кандидаты — 20 ближайших по
эмбеддингам задач из KB). Принимаем вариант при вероятности ≥ 0.55, иначе оставляем решение правил/эмбеддингов.
Без LLM (режим `fast`) роль/отрасль/задача/категория определяются ближайшими записями KB по эмбеддингам с порогами,
а `off_topic` — по отсутствию сущностей и низкому сходству со всем каталогом и KB.

Параллелизм: отбор кандидатов по «правильному» пониманию запускается сразу, не дожидаясь Jev; если Jev изменил сценарий или
фильтры — отбор повторяется (образец — `r36_engine/interpret_parallel.py`).

### 8.6. Контекст (`context.py`)

- **Категория страницы** (`category` в запросе): разрешает двусмысленность, даёт прибавку карточкам категории; для сценария
  `broad` — превращает запрос в `category`.
- **Профиль клиента**: сегмент → аудитория по умолчанию (`gov` → `gov`+`business`, `edu` → `edu`+`business`, остальные → `business`;
  `individual` → `home`); парк ОС → предпочтение совместимых; размер → количество по умолчанию для комплектов;
  купленные семейства → распознавание «продление» без названия продукта, выбор варианта «продление», пометка «у вас куплено».
- **Сессия**: если в новом запросе нет продукта/категории, но есть модификаторы («а на 50?», «подешевле», «на 3 года»,
  «а для линукс», «российский аналог») и предыдущий понятый запрос той же сессии был не более 10 минут назад — сущности
  наследуются (`carried`), в ответе чип «из предыдущего запроса» (его можно снять).
- Всё применённое из контекста видно в трассе и в `understood.chips` с пометкой источника.

## 9. Планы сценариев (`plans/`)

План получает `Understanding` + контекст и возвращает кандидатов и состав блоков ответа. Общий код — в `plans/base.py`.
Типы блоков ответа: `products`, `kit`, `analogs`, `answer`, `spec`, `compare`, `not_in_catalog`, `categories`, `vendors`,
`my_licenses`, `clarify`, `services`, `promo`, `lead`.

| Сценарий | Что делает план | Блоки | Приоритет |
|---|---|---|---|
| `sku` | точный артикул → карточка с выбранным именно этим предложением; несколько артикулов → список | `products` | P0 |
| `product` | карточки семейства (все редакции, названная — первой), вариант лицензии по параметрам запроса и профиля | `products`, `my_licenses`, `clarify` | P0 |
| `vendor` | витрина вендора: лучшие семейства по категориям, чипы категорий; если вендор ушёл — плашка и аналоги | `products`, `categories`, `analogs` | P0 |
| `category` | лучшее в категории с учётом фильтров и профиля, разнообразие по вендорам, уточняющие чипы | `products`, `clarify`, `categories` | P0 |
| `task` | задача → категории и семейства из `kb/use_cases.yaml` + смысловой отбор; объяснение «почему это решает задачу» | `products`, `clarify` | P0 |
| `role_kit` | слоты роли из `kb/roles.yaml`: в каждом слоте рекомендованный продукт (по профилю) и замены; итог на N мест | `kit` | P0 |

| `compliance` | фильтр по реестру/сертификатам/классу + карточка‑пояснение из `kb/compliance.yaml` | `answer`, `products` | P0 |

| `license_ops` | докупка/расширение, апгрейд, переход: соответствующие предложения; если таких нет — новые лицензии с примечанием | `products`, `answer` | P1 |
| `spec_list` | каждая строка разбирается отдельно (продукт, количество, срок, действие) → строка таблицы: найденное предложение, цена, сумма, уверенность, альтернативы; итог; нераспознанные строки отдельно; «всё в корзину», «запросить КП» | `spec` | P0 |
| `compare` | таблица сравнения 2–4 продуктов: вендор, происхождение, реестр, сертификаты, платформы, модель лицензии, цена от, редакции, для кого | `compare`, `products` | P1 |
| `question` | карточка‑ответ из `kb/faq.yaml` (поиск по вопросам: лексика + эмбеддинги) + связанные товары | `answer`, `products` | P0 |
| `broad` | уточнение: варианты смысла (упорядочены по профилю и категории) + лучшая догадка ниже | `clarify`, `products`, `categories` | P0 |
| `out_of_catalog` | честная карточка «этого продукта в продаже нет» (причина, если известна из KB) + аналоги + «запросить у менеджера»; спрос пишется в журнал | `not_in_catalog`, `analogs`, `lead` | P0 |
| `off_topic` | вежливый ответ + популярные категории; бессмыслица — подсказка формата запроса | `categories` | P0 |
| `account` | ответ из FAQ + блок лицензий клиента (что куплено, что скоро истекает) | `answer`, `my_licenses` | P1 |
| `service` | товары с `kind=service|course` по продукту/категории, иначе — ответ и заявка | `services`, `lead` | P2 |
| `promo` | товары с пометкой акции (mock) в контексте вендора/категории | `promo`, `products` | P2 |

Общие правила для всех планов:

- **Лестница ослабления.** Если после жёстких фильтров пусто или мало (< 3 карточек): снимаем ограничения по одному в порядке
  поставка → срок → диапазон количества → аудитория → версия → редакция → платформа → цена; на каждый снятый фильтр — примечание
  в `notes` («на 3 года нет — показаны лицензии на 1 год»). Вендор, исключения и регуляторика (реестр, сертификаты) не снимаются
  молча: если из‑за них пусто — честно говорим и предлагаем варианты без них отдельным блоком.
- **Пустой результат** — всегда содержательный ответ: что поняли, почему пусто (причина из закрытого списка, раздел 14.3),
  ближайшие альтернативы, заявка менеджеру. «Ничего не найдено» без объяснения недопустимо.
- **Уточнение (`clarify`).** До двух вопросов‑чипов, выбранных по наибольшей пользе: параметр, который сильнее всего делит найденное
  (количество, платформа, реестр, срок, редакция), либо подсказка из KB. Нажатие чипа — тот же запрос с добавленным фильтром.
- **Федеративность.** К основному блоку добавляются побочные, если они уместны: `my_licenses` (у клиента есть этот продукт),
  `analogs` (продукт недоступен), `answer` (есть точное попадание в FAQ), `categories`/`vendors` (навигация).

## 10. Отбор кандидатов и выбор варианта лицензии

### 10.1. Отбор

Кандидаты‑карточки собираются из источников (каждый оставляет метку источника для трассы): сущностные (семейство, редакция,
вендор, категория, задача → семейства, роль → слоты, аналоги), текстовые (BM25F по `residual` + словам сущностей), символьные,
смысловые (эмбеддинги). Объединение → маски фильтров и исключений → не более 300 кандидатов.

### 10.2. Выбор варианта (`rank/variants.py`) — **ключевая особенность ПО**

Для карточки выбирается лучшее предложение под запрос и профиль:

1. жёсткий отбор: действие (из запроса; иначе `renewal`, если клиент владеет продуктом и до истечения ≤ 90 дней; иначе `new`),
   аудитория (из запроса или сегмента), платформа, модель, поставка;
2. количество `N` (из запроса; для продления — купленное количество; иначе не задано): диапазон `qty_min ≤ N ≤ qty_max`;
   для пакетов — наименьший пакет ≥ N либо кратное число пакетов; без `N` — самый востребованный диапазон;
3. срок: из запроса; по умолчанию 12 месяцев (или самый популярный у семейства);
4. среди подходящих — по популярности, затем по цене;
5. расчёт `calc`: `qty`, `unit_price`, `total`, строка «30 × 1 890 ₽ = 56 700 ₽», НДС; «цена по запросу» — без расчёта, с кнопкой заявки;
6. если точного варианта нет — ближайший + примечание, что именно не совпало.

В карточке возвращаются выбранное предложение, ещё до пяти вариантов (соседние диапазоны, другой срок, продление/новая) и
счётчик всех вариантов; полный список — `GET /api/card/{card_id}`.

## 11. Релевантность и реранк

`rel0` карточки ∈ [0,1] — смесь: сущностное совпадение `ent` (семейство и редакция названы — 1.0; аналог или слот комплекта — 0.8;
задача из KB — 0.7; категория — 0.55; вендор — 0.5), лексика `lex` (BM25F, насыщение `s/(s+k)`), символы `chr`, смысл `sem`
(косинус, приведённый к [0,1]). Формула по умолчанию: `rel0 = max(ent, 0.45·lex + 0.15·chr + 0.40·sem)` с прибавкой за совпадение
нескольких независимых источников. Коэффициенты — в `config`, подбираются на `eval/`.

**Jev‑реранк** (`rank/rerank.py`, режим `smart`): верхние 30 карточек (настраивается) пакетами по 20 вопросов; вопрос на карточку —
«подходит ли товар под запрос с учётом понятого намерения»: `yes | part | no`; `rr = P(yes) + 0.5·P(part)`; `rel = 0.5·rel0 + 0.5·rr`.
Состояние запроса для Jev включает исходный запрос, исправление, сценарий, фильтры и сегмент клиента. Результаты кэшируются по
(хэш схемы, запрос, контекстный ключ, карточка). Для сценариев `sku`, `spec_list`, `account` реранк не нужен.

**Полосы релевантности** (`tier`):

| Полоса | Условие |
|---|---|
| 0 «точное» | продукт назван явно (артикул, семейство + редакция) или закреплён правилом `pin` |
| 1 «сильное» | Jev: `yes`; без Jev — `rel0 ≥ 0.62` или сущностное совпадение уровня семейства, аналога, слота комплекта |
| 2 «частичное» | Jev: `part`; без Jev — `0.40 ≤ rel0 < 0.62` |
| 3 «слабое» | остальное с `rel0 ≥ 0.22`; ниже порога — не показываем |

## 12. Бизнес‑ранжирование, персонализация, правила

### 12.1. Формула

Сортировка: сначала по полосе, внутри полосы — по
`score = w_rel·rel + w_pop·pop + w_margin·margin + w_pers·pers`, по умолчанию `0.50 / 0.20 / 0.15 / 0.15`;
множители: недоступно к покупке ×0.6, «цена по запросу» ×0.95. Веса хранятся в SQLite (`kv`), меняются ползунками в админке и
параметром `weights` запроса (для предпросмотра). **Гарантия:** карточка полосы *k* всегда выше любой карточки полосы *k+1*
при любых весах — проверяется тестом и показывается в аналитике («инверсий полос: 0»).
Каждая карточка несёт `score.parts` (вклады слагаемых) и `score.why` (человеческие причины).

### 12.2. Персональная составляющая `pers` ∈ [0,1]

Сумма с насыщением: продукт уже куплен клиентом; тот же вендор, что в истории; совместимость с парком ОС клиента;
соответствие сегменту (`gov` → в реестре и/или сертифицировано; `edu` → есть образовательная редакция; `smb` → есть малые
диапазоны и цена в нижней половине категории; `enterprise` → есть крупные диапазоны, корпоративные редакции);
категория из истории покупок; клики текущей сессии. Гость → `pers = 0`.
Жёсткие эффекты сегмента (не вес, а отбор): образовательные и «гос» редакции не показываются тем, кому они не положены
(либо показываются с пометкой «только для …», если запрос прямо о них).

### 12.3. Популярность и маржа

`pop` и `margin` — процентильные ранги внутри категории (чтобы дорогие категории не давили дешёвые), карточка берёт значения
выбранного предложения. Если в каталоге нет популярности — считается из журнала (клики, корзины, заказы за 90 дней с затуханием).

### 12.4. Разнообразие

Для сценариев `category`, `task`, `broad`, `compliance`: в первых шести позициях не более двух карточек одного вендора и одной
карточки на семейство (редакции сворачиваются, в карточке — «ещё N редакций»). Для `product` и `vendor` — не применяется.

### 12.5. Правила мерчандайзинга (`rank/merch.py`)

Таблица `rules`: `pin` (закрепить на позиции), `boost`/`bury` (множитель внутри полосы), `ban` (скрыть), `synonym` (фраза → сущность
или фраза), `redirect` (запрос → категория/сценарий), `banner` (плашка). Условие срабатывания: точный запрос, шаблон, сценарий,
категория, сегмент. Применение — после ранжирования, каждое срабатывание в трассе. Правила создаёт человек в админке или агент
(через одобрение предложения, раздел 14.4).

## 13. Подсказки (`suggest/`)

`GET /api/suggest` — без LLM, цель < 30 мс. Источники: популярные запросы журнала, семейства, вендоры, категории (все со своими
`aliases`, включая жаргон, транслит и варианты в неверной раскладке), вопросы FAQ, личное (купленные продукты клиента).
Алгоритм: префикс по последнему слову + совпадение предыдущих слов; если мало — перекладка раскладки, затем нечёткий поиск
(RapidFuzz) по тем же ключам. Ранжирование: частота запроса, популярность, персональная прибавка, категория страницы.
Ответ — группы: `queries` (дополнения запроса), `products`, `categories`, `vendors`, `my` (действия вроде «Продлить Kaspersky
Endpoint Security — истекает через 21 день»), `answers` (вопросы FAQ), плюс `corrected` (если запрос исправлен).
**Связанные запросы** (в ответе поиска, `related.py`): совместная встречаемость в сессиях журнала + соседние по сущностям
(другая редакция, продление ↔ новая, аналог, комплектующие продукты «с этим покупают») — 4–8 штук.

## 14. Журнал, аналитика, агент для бизнеса (`analytics/`)

### 14.1. Хранилище — SQLite `var/data/kuznitsa.sqlite` (WAL)

- `searches(search_id, ts, session_id, client_id, segment, source, engine, mode, q_raw, q_norm, q_corrected, intent, intent_conf,
  category_ctx, entities_json, filters_json, n_cards, zero, relaxed, fail_reason, top_cards_json, blocks_json, ms, llm_calls,
  llm_cost_usd, cached, trace_json)`; `source` ∈ `ui|gallery|compare|api|replay|eval|history`; `engine` ∈ `kuznitsa|naive|legacy`.
- `events(event_id, ts, search_id, session_id, client_id, type, card_id, offer_id, position, qty, value, margin_value, payload_json)`;
  `type` ∈ `impression|click|cart|order|exit|reformulate|suggest_show|suggest_click|correction_accept|correction_reject|chip|lead`.
- `llm_calls(id, ts, search_id, kind, model, cached, tokens_in, tokens_out, cost_usd, ms, ok)`, `llm_cache(key, kind, schema_hash,
  response_json, cost_usd, created_at, hits)`.
- `rules(...)` (раздел 12.5), `insights(...)` (14.4), `replays(...)`, `eval_runs(...)`, `kv(key, value)`.

В KPI по умолчанию входят `source IN (ui, replay, history)`; `compare`, `gallery`, `eval` — отдельно.

### 14.2. Показатели (формулы — в коде и в подсказках интерфейса)

Число поисков и сессий; **доля запросов без результата** (нет карточек в блоках `products|kit|analogs|spec`); **неудачный поиск**
(без результата либо без клика с последующим уходом или переформулировкой); **уходы после неудачного поиска**; CTR и средняя
позиция клика, MRR; **конверсия поиска в корзину и в заказ**; выручка и маржа из поиска; доля исправленных запросов и принятых
исправлений; доля поисков через подсказку; время до первого клика; **оценка потерянных заказов в рублях** =
Σ по неудачным поискам `P(заказ | удачный поиск того же сценария и категории) × средний чек того же среза` (показываем и
осторожную оценку с понижающим коэффициентом); распределение сценариев; спрос по категориям, вендорам, сегментам.

### 14.3. Причины неудач — закрытый список

`not_in_catalog_known` (продукт известен KB, в каталоге нет) · `not_in_catalog_unknown` (похоже на продукт, неизвестен) ·
`vendor_left` (вендор ушёл с рынка) · `vocabulary_gap` (слово не знаем: нужен синоним) · `typo_unfixed` · `filters_too_strict`
(нет такого срока/диапазона/редакции) · `price_on_request_only` · `content_gap` (в карточке нет атрибута, по которому ищут) ·
`ranking_issue` (нужное было ниже пятой позиции) · `ambiguous` · `sku_not_found` · `hardware` · `piracy` · `off_topic` · `gibberish`.
Определяется правилами по трассе; спорные случаи в режиме с LLM досматривает Jev (пакетно, офлайн).

### 14.4. Агент: предложения действий (`insights.py`)

Агент периодически (и по кнопке) разбирает журнал и создаёт **предложения** с доказательствами и ожидаемым эффектом:

| Тип | Кому | Суть | Что происходит при «Применить» |
|---|---|---|---|
| `add_synonym` | контент | неизвестное слово, которое люди потом переформулируют в известное | правило `synonym` → слово сразу понимается |
| `add_product` | контент, продукт | кластер спроса на то, чего нет в каталоге (число запросов, клиенты, сегменты, оценка ₽) | задача «завести товар» (mock) + временная плашка с аналогами |
| `fix_card` | контент | у товаров нет атрибута, по которому ищут («для linux», срок, реестр) | список карточек на доработку (mock‑задача) |
| `merch_rule` | менеджер e‑com | запрос с низким CTR, где кликают позицию ниже пятой | правило `pin`/`boost` |
| `rising_demand` | продукт | растущие запросы и категории | отметка, попадает в дайджест |
| `hot_lead` | менеджер e‑com | крупный клиент искал и не нашёл или смотрел «цена по запросу» | заявка менеджеру (mock) |
| `renewal_campaign` | менеджер e‑com | клиенты, у кого лицензии истекают в ближайшие 30 дней | список для рассылки (mock) |
| `weights_advice` | руководитель | как изменение весов популярности/маржи меняет выручку и релевантность на журнале | предпросмотр и применение весов |

У предложения есть статус `new → applied|rejected → verified`: после применения затронутые запросы прогоняются заново и
результат «до/после» сохраняется. Дайджесты по ролям (`digest.py`) — шаблонные тексты из тех же чисел; при заданной
`KZ_GEN_MODEL` формулируются генеративной моделью, но числа берутся только из расчётов.

### 14.5. Наивный поиск и сравнение (`naive.py`, `replay.py`)

`naive`: нижний регистр, разбиение по пробелам, **все** слова должны входить подстрокой в название SKU, сортировка по
популярности, без исправлений и синонимов — так устроен типовой встроенный поиск магазина. Используется как `mode=naive`,
в сравнении и при генерации исторического журнала.
`replay`: прогон журнала запросов (уникальные запросы с частотами) через `naive` и через `kuznitsa`; итог: доля без результата,
доля запросов с целевым товаром в первых пяти (для mock — по скрытой разметке генератора; для чужого журнала — оценка
Jev‑судьёй «в первых пяти есть подходящее»), оценка потерянных заказов, список «было пусто → стало найдено» с примерами.
Импорт чужих данных: адаптер журнала запросов (текст, время, клиент, число результатов, клик/заказ — что есть) и адаптер
выгрузок Метрики (отчёт «поисковые фразы на сайте», сырые визиты и хиты с целями и электронной коммерцией) → `searches`/`events`
с `source=history`, `engine=legacy`.

## 15. LLM‑слой (`llm/`)

- `jev.py`: `decide(state: str, questions: dict) -> answers` поверх Decisions API (формат запроса и разбор ответа — как в
  `r36_engine/llm.py`); таймауты (соединение 2 с, ответ 6 с), один повтор, ограничение параллелизма, «предохранитель»
  (после 5 ошибок подряд LLM выключается на 60 с, ответы идут в режиме `fast` с пометкой в трассе); `httpx` с `trust_env=True`.
- `cache.py`: кэш в SQLite по ключу (хэш схемы вопроса, нормализованное состояние); учёт попаданий.
- `cost.py`: стоимость вызова из `usage.cost`, иначе по токенам; агрегаты на запрос и за период; в ответе поиска — блок `cost`.
- `textgen.py`: необязательная генеративная модель (по умолчанию выключена).
- Тесты используют подставной транспорт; обращений в сеть из тестов нет.

## 19. Mock‑данные (`mock/`, `cli build-mock`)

Подробный проект — `mock/spec/` (Argon). Пока его нет, действуют правила ниже; когда появится — привести в соответствие.
Всё детерминировано (`--seed`, по умолчанию 20261126), в данных и интерфейсе помечено как mock.

- **Каталог**: каждое KB‑семейство с `catalog: yes` разворачивается в предложения: редакции × действия × сроки × диапазоны
  (или пакеты) × аудитории × поставка — не декартово, а по правдоподобным шаблонам вендора (`naming.py`: стиль названий
  Kaspersky, Microsoft, 1С, Astra, Dr.Web, «МойОфис» и т. д.; образцы — в `/home/bb/kuznitsa-softline-ref/softline/`).
  Цена — от `price_rub.typical` с коэффициентами диапазона, срока, действия (продление дешевле новой), аудитории;
  часть — «цена по запросу»; часть — недоступна. Маржа — по категории и вендору с шумом; популярность — из `popularity` 1..5 и
  закона Ципфа. Артикулы — синтетические, в узнаваемом стиле вендора. Цель — 15–25 тыс. предложений.
  Если KB ещё почти пуста — использовать встроенный запасной набор из 40 семейств, чтобы всё запускалось.
- **Клиенты**: ~200, сегменты и отрасли, размер, парк, история заказов за два года с продлениями; 8 демо‑профилей (раздел 3.3).
- **Журнал запросов за 90 дней** (60–100 тыс. поисков): у каждого запроса скрытая разметка генератора (целевое семейство или
  категория, сценарий, вид искажения); распределение «голова/середина/хвост»; искажения — опечатки, неверная раскладка,
  транслит, жаргон; запросы о том, чего нет в каталоге; сезонность отчётных периодов. Исход каждого поиска моделируется
  **наивным поиском**: пусто → уход или переформулировка; есть целевой товар → клик → корзина → заказ с вероятностями по сегменту.
  Это «журнал старого поиска» (`source=history`, `engine=legacy`).
- **Выгрузки в духе Метрики**: отчёт по поисковым фразам сайта и сырые визиты/хиты с целями и электронной коммерцией —
  из тех же сессий (файлы в `var/data/mock_metrika/`), чтобы проверять адаптеры импорта.

## 20. Качество

- **Модульные тесты** (`tests/`, pytest, без сети): нормализация и токены ПО; ремонт (раскладка, транслит, опечатки, «не трогать
  версии и артикулы»); разбор количества/срока/цены/действия; разбор названий SKU; лексикон и двусмысленность; правила сценариев;
  выбор варианта лицензии; полосы и гарантия отсутствия инверсий; персонализация (один запрос — разные профили — разная выдача);
  лестница ослабления и примечания; подсказки; журнал и показатели; предложения агента (применил → поведение изменилось);
  API через `fastapi.testclient.TestClient` (сокеты не открывать); кэш и стоимость LLM на подставном транспорте.
- **Проверочные запросы** (`eval/queries.dev.jsonl`, `eval/queries.holdout.jsonl`, пишет Argon). Строка:
  `{"id","q","scenario","profile","category_ctx","expect","assert"}`. Ключи `assert`: `intent`, `vendor`, `family_any`, `action`,
  `model`, `qty`, `metric`, `term_months`, `platform`, `audience`, `registry`, `certs`, `price_max`, `category`, `exclude_vendor`,
  `top5_any`, `top1_any`, `must_not`, `block_any`, `zero_ok`, `corrected_to`, `lines`. Названия сопоставляются с заголовками карточек
  подстрокой без учёта регистра, а с понятыми сущностями — через лексикон. `python -m kuznitsa.cli eval <файл> [--mode fast|smart]`
  печатает долю пройденных по сценариям и по ключам, пишет `var/data/eval/<метка>.jsonl` и сводку в `eval_runs`;
  `cli eval-compare <A> <B>` — что изменилось и что стало хуже. Holdout запускает только архитектор.
- **Судья** (`eval/judge.py`, P1): оценка первых десяти карточек категоризатором (`yes|part|no`) → взвешенная точность, как в r36.
