# Консоль «Кузница Softline»

AiXenix · контракт B4 (§27.7, §28.3, §28.7). Базовый путь `/api/admin`. Для крупных ответов поддерживается gzip. Примеры KPI и предложений получены на 45 000 поисков. В примере импорта использованы отдельный каталог и четыре внешних файла. Идентификаторы предложений, правил и прогонов берите из ответа сервера.

Для чтения и записи передавайте `X-Admin-Token`, равный `KZ_ADMIN_TOKEN`. При `KZ_ADMIN_OPEN=1` чтение доступно посетителю демо. Кнопки изменения данных требуют токена. Секрет передаёт серверная часть консоли. Ответы об ошибке содержат `error.code` и `error.message`. Код 403 означает отсутствие доступа, 404 — неизвестный идентификатор, 422 — неверные параметры или недопустимый переход состояния.

## Как читать показатели

`totals` и `slices` возвращают доли от 0 до 1, суммы в рублях и время в секундах. В плитках процент уже умножен на 100. Окно истории и подпись источника находятся в `scope`. Сумма дневных счётчиков равна `totals.searches`. Открытая московская дата имеет признак `partial`. Отдельный объект `today` считает живые обращения на стенде. Служебные поиски исключены из обоих знаменателей.

На синтетической истории «до» означает обычный поиск по словам. В паре каждая фраза имеет вес своей исторической частоты. У попадания в топ-5 собственный знаменатель размеченных целей. Для обычной корпоративной закупки целью может быть доступный по открытой цене коммерческий SKU нужного семейства, новый на год или бессрочный. Для остальных целей учитываются семейство или категория. Поиск Кузницы воспроизведён без профиля покупателя в быстром режиме. Только наличие товара и его позиция наблюдаются в повторе. Для заказов и уходов API помечает прогноз по модели кликов, откалиброванной на исходах истории. В `order_amounts` доступны медиана, среднее и максимум наблюдавшегося чека. [Компактные KPI](admin_examples/kpi-overview.json)

Каждая роль получает в `digest.items[].findings` вывод, действие и адрес доказательства. API проверяет роль до обращения к журналу. Кэш сводок хранится в SQLite. Загрузка истории и публикация парного прогона обновляют расчёты. Вкладки могут читать одну и ту же версию снимка параллельно.

`lost_orders` оценивает один потенциально потерянный заказ на неудачную сессию. Сессии с корзиной, заявкой, заказом или нецелевой тематикой исключаются. Конверсия и медианный чек успешных сессий берутся по сегменту, категории и сценарию с укрупнением среза при нехватке наблюдений. Обе оценки и коэффициенты доступны в ответе. Эффекты разных предложений могут относиться к одной сессии. Складывать их на панели руководителя нельзя.

Агент возвращает роли `content_manager`, `product_manager`, `ecom_manager`, `head_ecom`. В дайджесте также есть `customer`. При `confidence: null` скрывайте строку уверенности. Для продлений `evidence_text` содержит дату, число клиентов и договоров. Число `confidence` — эвристика объёма наблюдений, равная числу сессий / (число сессий + 20). В карточке показывайте примеры фраз, число сессий и пояснение `impact.formula_note`. Для проверки показывайте обе выдачи, в том числе ухудшения. Статус `verified` означает, что сравнение сохранено.

## Правила

Условия `phrase` (точная нормализованная строка), `pattern` (маска с `*` и `?`), `intent`, `category`, `segment`, `start` и `end` (Unix seconds, правая граница исключена) объединяются по И. Поле действия зависит от вида правила.

| kind | action |
|---|---|
| synonym | `{"phrase":"резервилка","kind":"text","to":"Кибер Бэкап"}`. Виды сущностей доступны по контракту лексикона. |
| redirect | Одна цель `q`, `category` или `intent`. Поддерживает контекст. |
| pin / ban | `card_id`. Для закрепления задаётся `position` от 1. |
| boost / bury | `card_id` и положительный `factor`. Перестановка внутри одного яруса. |
| banner | `{"text":"Уточните условия поставки"}`. |

## Импорт

`gen-history --seed 20261126 --today 2026-11-26` воспроизводит журнал на фиксированную дату. Команда заменяет только историю генератора, чьи ID начинаются с `s_mock_`. `gen-metrika` формирует три файла в `var/data/mock_metrika`.

`import-history файл [файл ...] [--mapping карта.yaml]` принимает CSV и TSV в UTF-8 или Windows-1251, XLSX с преамбулой и шапкой, JSONL. `--mapping путь/к/карте.yaml` задаёт, например, `{"Фраза посетителя":"q","Сколько раз":"count","Найдено":"n_cards"}`. Для агрегированного отчёта число поисков восстанавливается по частоте, доля нулей округляется до числа наблюдений. Если времени нет, используется дата изменения файла. Отчёт каждого файла содержит распознанные и неизвестные заголовки, пропуски с причинами, дубли и доступность показателей. «Визиты» задают число визитов, если число поисков не передано. При агрегированных отказах атрибуция к поиску приблизительна. В отчётах `order_denominator` содержит число наблюдений с известным исходом заказа. Цель для ранжирования берётся из явной разметки или идентификатора заказанного либо выбранного товара. Если цель неизвестна для всей выборки, элемент `top5_hit` отсутствует в `pairs`, а причина указана в `coverage_notes`.

`import-history var/data/mock_metrika` читает визиты и хиты из каталога. CSV с агрегатами — альтернативное представление того же трафика. Импорт упорядочивает хиты каждой таблицы по времени. Для визитов, разбитых между несколькими таблицами хитов, соедините части в один файл со сплошной шапкой. Атрибуция событий идёт к последнему поиску в этом визите. Сегмент гостя из внешнего файла без метаданных — `unknown`. Для проверки сходимости импортируйте сырые выгрузки в отдельный журнал.


На примерах можно воспроизвести всю загрузку. Команды запускаются в корне рабочей копии с подготовленным каталогом. Входные файлы представляют разные записи. После импорта консоль показывает загруженную историю, а `gen-history` возвращает демонстрационное окно.

```bash
python -m kuznitsa.cli import-history docs/admin_examples/import/vendor-actions.tsv docs/admin_examples/import/vendor-traffic.tsv docs/admin_examples/import/onsite-report.xlsx docs/admin_examples/import/supplier-search.csv
python -m kuznitsa.cli replay --mode fast
python -m kuznitsa.cli insights
```

Для проверки доступности заказов, выручки, кликов и исходной выдачи смотрите `availability` в отчёте каждого файла. [Разбор четырёх входных файлов](admin_examples/import-history.json)

Открывайте `/admin#head` для парных показателей и `/admin#log` для живых запросов. Для показа веса маржи на запросе «аналог teamviewer» выставьте 0,45 релевантности, 0,15 популярности, 0,25 маржи и 0,15 профиля. Предпросмотр показывает сумму удельной маржи пятёрки до и после, изменение с учётом позиции и инверсии уровней. [Предпросмотр](admin_examples/preview.json)


## Данные одного экрана

На экране руководителя `scope_text` задаёт период и число поисков. До прогона показана вся активная история. После публикации прогона `totals`, `tiles`, `slices`, `funnel` и `pairs` относятся к одним историческим поискам в пределах выбранных фильтров. Это действует и при явном `limit`. Размеченная часть указана в `top5_hit.scope_text`. У `exit_after_fail` знаменатель — все поиски этой области, а `n_before`, `n_after` — числа уходов. Общий текст находится в `note`. Если деможурнал, файл целей, каталог или метод прогона принадлежат разным сборкам, ответ получает `data_status: "incompatible"`, `comparison: null`, пустые `pairs` и одно пояснение в `note`. Интерфейс в этом случае показывает пояснение. Импортированная история получает свой снимок при повторном прогоне. Отсутствие меток во внешнем файле скрывает только показатель попадания в топ‑5. [Ответ для несовместимой сборки](admin_examples/kpi-stale.json) Цвет берите из `tone`, подписанную разницу с единицами — из `delta_text`. Конверсия и уходы «после» помечены как прогноз по модели кликов. [Ответ с парами](admin_examples/kpi-overview.json)

`GET /api/admin/digest?role=<роль>&format=json|md|xlsx` поддерживает все пять ролей. JSON сохраняет контракт `items[].findings`. Для Markdown и Excel API отдаёт файл с `Content-Disposition: attachment`, именем роли и расширением. В файле есть период, показатели, действия и предложения. Для руководителя сравниваются потери и прогноз возврата, для продукта приведены частоты и рост, для контента — спрос и дефекты карточек. [Отчёт руководителю](admin_examples/head_ecom.md) · [Отчёт контент-менеджеру](admin_examples/content_manager.xlsx)

`GET /api/admin/ingest` возвращает оригинальный `catalog` из `import_report.json`, фактический `classification_usd = catalog.ai.usd`, прогноз `forecast_usd`, массив отчётов `history` и до 50 строк `review` из `import_ai.jsonl`. При отсутствии отчёта стоимость равна null. Сначала идут решения с переходом на запасной способ и отклонённые назначения, затем решения с низкой уверенностью. Каждый исходный файл истории имеет карту `columns`, границы `period` (Unix time), `rows_read`, `rows_accepted`, `skipped`, `skip_reasons`, `observed_searches`, `observed_empty` и их отношение `zero_rate`. Доля равна null, если исходный размер выдачи отсутствует у всех записей. Файл `$KZ_DATA_DIR/history_report.json` сохраняет те же отчёты под ключом `files`. [Данные и очередь](admin_examples/ingest.json)

Таблицы Logs API связываются по `visitID` или списку `ym:s:watchIDs`, порядок входных файлов в одной команде произвольный. Только визиты со стартовой поисковой страницей можно импортировать отдельно. При наличии хитов приоритет имеет поиск с фразой в URL или параметрах события. Покупки визита при отсутствии ecommerce-событий относятся к последнему поиску этого визита. Отчёт «Поисковые фразы» может содержать внешний поисковый трафик. Для анализа внутреннего поиска выбирайте соответствующий срез Метрики. Передавайте связанные файлы одним вызовом import-history. Сопоставление поисков и сверка отчёта описаны ниже.

В ответе `POST /api/search` в режиме `naive` сравнивайте по `card_ref || card_id`. [Строка обычной выдачи](admin_examples/naive-row.json)

В обычной выдаче `card_id` с префиксом `sku:` открывает выбранный SKU, `card_ref` объединяет варианты. Для маршрута `GET /api/admin/ui/search-reference?q=…` подготовлена проекция `{search_id, items: [{card_id, position, offer_id?}]}` с каноническим идентификатором. Подключение к обработчику в зоне C приведено в отчёте B3.

В `add_synonym` строка `evidence_text` описывает исходную выдачу и позицию цели в пробном правиле. Применение повторно проверяет исходную выдачу. Поле `verification.outcomes[]` даёт число карточек до и после, позицию цели и оба `search_id`.

| POST /priorities/import | Принять снимок атомарно. По умолчанию обновляются перечисленные ID. Явный `"mode":"replace"` восстанавливает весь набор и записывает удаления в аудит | [Импорт](admin_examples/priorities-import.json) |

В `target` допустимы `categories` с подразделами, `vendors`, `families`, `cards`, `tags` и `price_rub: {"min":число,"max":число}`. Границы необязательны. Внутри списка достаточно любого совпадения, между полями должны выполняться все условия. Критерии и признаки перечислены в ответе списка. В `scope` доступны сегменты, профили, регионы, виды запросов, нормализованные подстроки, каналы и включительные даты `from` и `to`. Действие включает `boost` от −100 до 100, неотрицательные веса `criteria`, квоту `max_in_top: {"n":5,"k":2}`, закрепление `pin: {"card_id":"…","position":1}` и публичную подпись. Порядок и разрешение сдвига на соседний уровень задают `order` и `cross_tier` на верхнем уровне.

За последние 24 часа `searches_in_scope_24h` считает поиски витрины, виджета и API в области правила. `fired_24h` считает уникальные поиски с ID правила в шаге business. `share_top5` — доля подходящих позиций среди измеримых позиций первых пяти. В старом архиве иногда отсутствует выбранный SKU для проверки цены или признака. Число таких позиций указано в `unknown_positions`.

Предпросмотр дважды вызывает быстрый `Engine.preview` для одной пары фраза–профиль. Существующее правило заменяется по ID. Для каждой пары возвращаются первые пять карточек, частота и число изменённых позиций. Доли и маржа взвешены по числу поисков. Маржа в рублях за единицу равна сумме `цена × доля маржи` выбранных SKU с ценой, делённой на число таких позиций. Число затронутых поисков охватывает только проверенную выборку. Оценка заказов направления равна округлённой вниз сумме произведений числа поисков с заказом на положительное изменение доли направления. Это сценарий перераспределения исторических покупок. При отсутствии наблюдений о заказах `orders_estimate` равен null. Исторический канал при его отсутствии моделируется выбранным каналом. Подробности возвращаются в `summary.note`.

## Источники событий и заявок

`sniff(path)` возвращает `kind`, `confidence`, словарь «исходная колонка → поле» в `columns` и пояснение `reason`. Распознаются `search_log`, `metrika_hits`, `metrika_visits`, `metrika_report`, `metrika_external_phrases`, `ga4_events`, `crm_leads`, `orders` и `unknown`. Импорт читает таблицу после служебных строк. При наличии преамбулы период и итоги сохраняются в `report_metadata`. `report_metrics` суммирует строки отчёта, один визит может содержать несколько разных фраз.

- **Внутренний поиск.** При одновременной загрузке точное совпадение визита, времени и текста связывает хит с поиском магазина. При совпадении частот всех фраз с журналом отчёт Метрики сохраняется как сверка (`summary_only`). Прямой переход с выдачи на страницу товара учитывается как клик. Событие покупки или покупка в сводке визита подтверждают заказ.
- **GA4 BigQuery.** Экспорт в JSON Lines передаётся в `import-history`. Сессия определяется сочетанием `user_pseudo_id` и параметра `ga_session_id`. Время BigQuery задаётся в микросекундах. Поиск берётся из `view_search_results` или `search` с `search_term`. После поиска учитываются `select_item`, `add_to_cart` и `purchase`. В событии покупки сохраняются позиции, валюта и исходная сумма. В рублёвый оборот попадают покупки с известной суммой в RUB. [Пример GA4](admin_examples/import/ga4-bigquery.jsonl)
- **Заявки CRM.** Заявка хранится отдельно вместе с суммой. Семидневное окно связывает её с последним поиском того же клиента по фразе или товару. Для даты без времени используется конец дня. Идентификатор заявки защищает от повторного импорта. Заявки без подходящего поиска остаются в `crm_leads[].unlinked` до появления истории. Воронка содержит отдельные этапы `orders`, `leads` и `orders_or_leads`. Последний считает поиски с любым из двух результатов один раз. Сумма заявки в `pipeline_rub` относится к потенциальным продажам. [Пример CRM](admin_examples/import/crm-requests.csv)
- **Внешние поисковые фразы.** Отчёт о привлечении сохраняется отдельно с числом визитов и верхними 50 фразами. Поле `GET /ingest → external_phrases` предназначено для раздела «Данные». Этот источник добавляет ноль поисков в знаменатель внутренней воронки. Для отчёта по внутреннему поиску используйте заголовок «Фраза внутреннего поиска» или заголовок отчёта «Поиск по сайту». [Пример отчёта о привлечении](admin_examples/import/external-acquisition.csv)

На трёх образцах получаются два внутренних поиска, один заказ, две связанные заявки и два поиска с заказом или заявкой. Ещё одна заявка ожидает привязки. Внешний отчёт содержит 930 визитов. [Ответ раздела «Данные»](admin_examples/ingest-channels.json) · [Показатели и воронка](admin_examples/kpi-channels.json)

Отчёт Метрики «Достижение целей» распознаётся как `metrika_goals`. В `GET /ingest` и `history_report.json` у файла есть исходные `goals_by_day`, итоги `report_metrics` и строка `reconciliation_text`. Она также видна в разделе «Данные». Разность считается как достижения Метрики минус события журнала за сопоставимые дни по московскому времени. При пересечении двух выгрузок одной цели за тот же день используется последняя загруженная величина.

В `GET /kpi` и `GET /kpi?day=YYYY-MM-DD` поле `funnel_daily[].stages` содержит для каждого этапа `metrika`, `journal`, принятое `count` и `source` (`journal` или `metrika_goals`). Ноль при наблюдении заказов в журнале сохраняется. Отсутствующее наблюдение представлено `null`. Воронка включает агрегаты там, где нет наблюдений, с подписью источника. Состав покупателей, пересечение заявок и заказов и выручка по таким агрегатам неизвестны. Для срезов по клиенту, категории, сценарию и частичного парного прогона агрегаты не распределяются. Выгрузка менеджера e-com включает раздел «Цели по дням». [Пример входного CSV](admin_examples/import/goals-by-day.csv)

### Страницы API Метрики и обращения покупателей

`import-history` принимает JSON-страницы `/stat/v1/data` в любом порядке. В `GET /ingest` и в массиве `history_report.json → files` появляется одна запись `metrika_api` на запрос отчёта. Поля `report_id`, `files`, `pages`, `query` связывают её с выгрузкой. Период, фильтры, измерения и показатели входят в идентификатор. `rows_read` учитывает строки всех страниц, `rows_accepted` — уникальные сочетания измерений, `duplicates` — пересечения, `skip_reasons` — ошибки строк. `complete` означает совпадение с `total_rows` при согласованных данных, `sampled` передаёт признак выборки Метрики. В `report_metrics` сохраняется общий `totals` из ответа API.

В `external_phrases` и `external_engines` перечислены источники привлечения. `site_phrases` содержит запросы из параметров URL, например `/search?q=backup+pro`. В подборках до 50 значений с полями `q`, `count`, `metric`. Частота выражена в визитах или просмотрах согласно исходному показателю. Если передана только доля отказов, частота неизвестна и равна `null`. Агрегаты сохраняются отдельно от событий воронки.

`GET /support` отдаёт число обращений `messages`, известных клиентов `clients`, темы `topics`, упомянутые товары `products` и примеры вопросов `unanswered`. `unanswered_count` считает обращения, для которых при импорте не нашлось достаточно близкого вопроса с ответом в FAQ. Вкладки контент-менеджера и продукт-менеджера показывают один и тот же срез. Для входного CSV с датой, клиентом и текстом вопроса `sniff` возвращает `support_chat`. Товар и артикул можно передать отдельными колонками. У предложений по таким обращениям `evidence.source = support_chat`, в `evidence.questions` лежат вопросы-примеры, в `evidence.examples` — запрос и идентификатор контрольного поиска.

Воспроизводимый набор для `import-history` содержит две страницы внешних фраз, отчёт по внутренним URL и обращения в Windows-1251. [Входные файлы](admin_examples/import/api-chat/) · [Ответ GET /support на контрольном каталоге](admin_examples/support.json)

Событийный JSON Lines распознаётся как `kind=search_log`, `format=site_events`. Метка времени и сессия обязательны. Показ выдачи уточняет число результатов связанного поиска. Клик, корзина и заказ привязываются к ближайшему предшествующему поиску той же сессии. Внутри файла строки сортируются по времени, при равенстве первым учитывается поиск. Сумма и маржа заказа учитываются при наличии исходной суммы в рублях и, для маржи, известного предложения каталога.

В отчёте импорта `events_by_type` содержит число уникальных принятых событий файла по типам `search`, `impression`, `click`, `cart`, `order`. Их сумма равна `rows_accepted`. Поле `inserted_by_type` показывает, сколько из них добавил текущий импорт. Дубли внутри файла вынесены в `repeated_rows`, события до первого поиска сессии и некорректные строки — в `skipped` и `skip_reasons`. [Пример событий в произвольном порядке](admin_examples/import/site-events.jsonl)

## Допродажи

Базовые правила из `$KZ_KB_DIR/upsell_r9.yaml` дополняются правками магазина в SQLite. Условие `when` принимает `classes`, `families`, `vendors`, `query_words`. В `offer` доступны те же поля, кроме слов запроса. Правило срабатывает при совпадении первой основной карточки с одним из условий или при вхождении одного из выражений в запрос. Цели объединяются по классам, линейкам и вендорам. Вес лежит между 0 и 1. Чтение и предпросмотр доступны при открытом деморежиме. Изменение требует `X-Admin-Token`. Имя автора изменения можно передать в `X-Admin-Author`.

| Запрос | Назначение и пример ответа |
|---|---|
| GET /upsell | Действующая редакция каждого правила, состояние и счётчики. [Список](admin_examples/upsell-list.json) |
| POST /upsell | Полное правило с уникальным строковым id, when, offer и reason. По умолчанию включено, вес 1, источник kb. [Создание](admin_examples/upsell-create.json) |
| PUT /upsell/{id} | Частичная правка. Для изменения условий передайте целиком соответствующий объект when или offer. [Правка](admin_examples/upsell-update.json) |
| DELETE /upsell/{id} | Отключает правило. Вернуть в выдачу можно через PUT с enabled=true. [Отключение](admin_examples/upsell-disable.json) |
| POST /upsell/preview | Тело содержит q и rule_id либо q и полный черновик rule. С модулем A возвращает фактические места черновика в выдаче и в блоке crosssell. На движке до слияния показывает кандидатов отдельного правила. [Предпросмотр](admin_examples/upsell-preview.json) |
| GET /upsell/audit | Последние 200 изменений с автором и редакциями до и после. [Журнал](admin_examples/upsell-audit.json) |
| GET /upsell/analytics | Показы карточек, клики, добавления в корзину по правилам и до 30 пар «запрос → карточка» по убыванию числа корзин. [Сводка](admin_examples/upsell-analytics.json) |

Клиент отправляет по одному `POST /api/event` на показ карточки, клик и добавление в корзину. Пример тела — `{"type":"cart","search_id":"…","card_id":"…","payload":{"kind":"upsell","rule_id":"office_antivirus"}}`. Для отдельного блока допустимо `kind:"crosssell"`. Обязательна связь с поиском витрины. Управленческая сводка учитывает весь период событий витрины и показывает нули до первого события.

Для снимка настоящего фида команда `gen-history --feed --seed 20261126 --today 2026-11-26` создаёт синтетическую историю на 90 дней. При наличии файла D `feed_classes.json` команда выбирает этот режим автоматически. Команды `replay --mode fast` и `insights` строят пары и предложения. В `GET /kpi` источник указан в `history_note` и в общей подписи сравнения. Поле `failure_exits` показывает число уходов, число неудачных поисков и их отношение. В паре `exit_after_fail` знаменатель — все поиски.
