## 27.3 Частная и общая запись: поле `parent` у ролей и отраслей (пишет K, читает A)

- У записей `kb/roles*.yaml` и `kb/industries*.yaml` — необязательное поле `parent: <id записи той же группы>`: запись есть
  частный случай родительской (`dentistry_private_clinic` → `healthcare`, `college_spo` → `education`).
- Загрузчик: слово или фраза из `aliases`, заявленная и у родителя, и у потомка, принадлежит потомку — предупреждения
  о повторе нет. Неизвестный `parent` — предупреждение в `kb-check`, поле игнорируется.
- Разбор запроса: подходят и родитель, и потомок — выбирается потомок. В `understood.entities` и в подписи «Понято так» —
  потомок. У блока `kit` появляется необязательное поле `parent: {"id", "title", "q"}`: общий набор и готовый запрос к нему.
- Названа роль внутри отрасли («администратор в стоматологии», «бухгалтер в школе») — выбирается роль, отрасль остаётся
  условием.

## 27.4 Поиск по коду ОКВЭД (данные K, разбор A)

Покупатель‑юрлицо знает код своей деятельности. Файл `kb/okved_r4.yaml` — новая группа базы знаний:

```yaml
- {code: "86.23", title: "Стоматологическая практика", industry: dentistry_private_clinic}
- {code: "86",    title: "Деятельность в области здравоохранения", industry: healthcare}
```

- Сопоставление — по самому длинному совпавшему началу кода: `86.23.1` → `86.23` → `86.2` → `86`.
- Запрос распознаётся только со словом «оквэд» (иначе код не отличить от ОКПД2 и номера версии): «оквэд 86.23»,
  «ОКВЭД 62.01 что нужно из программ», «компания с оквэд 47.73». Код ОКПД2 и КТРУ — прежний сценарий требований.
- Ответ: сущность `{"type": "okved", "id": "86.23", …}` и сущность отрасли; намерение `industry`; условие в «Понято так» —
  «ОКВЭД 86.23 · Стоматологическая практика»; блок `kit`. Неизвестный код — блок `clarify` с причиной `unknown_term`.

## 27.5 Спецификация из файла и выгрузка коммерческого предложения (делает D, пользуется C)

**Загрузка.** `POST /api/spec/upload?name=<имя файла>&profile_id=<…>&mode=fast|smart&session_id=<…>`; тело запроса — сам файл
(`Content-Type: application/octet-stream`, без multipart), не больше 2 МБ. Форматы: `.xlsx`, `.csv`, `.tsv`, `.txt`
(UTF‑8 и Windows‑1251; разделители — точка с запятой, запятая, табуляция). Из файла берутся позиции: название, количество,
а если есть колонки — артикул и единица. Позиций — до 200, остальные попадают в `skipped`.

Позиции передаются движку обычным запросом (`source: "ui"`): одна позиция в строке, вид строки —
`<название> [<артикул>] — <количество> шт`. Поток A гарантирует: спецификация до 200 строк разбирается в быстром режиме
не дольше 3 с, артикул в строке главнее названия.

Ответ — обычный ответ поиска (та же модель, что у `/api/search`: `search_id`, `understood`, блоки с блоком `spec`, `trace`)
плюс поле `upload`:

```json
{"name": "spec.xlsx", "kind": "xlsx", "rows_total": 27, "positions": 23,
 "columns": {"title": "Наименование", "qty": "Кол-во", "sku": "Артикул", "unit": null},
 "skipped": [{"row": 4, "reason": "Пустое название"}]}
```

Ошибки — общим помощником `error(status, code, message)`: `file_too_large` (413), `file_unsupported` (415), `file_empty`
и `no_positions` (400); сообщение по‑русски, его показывает витрина.

**Выгрузка.** `GET /api/export/{search_id}?format=xlsx|csv` — файл `KP-<ГГГГММДД>-<первые 6 знаков search_id>.xlsx`. Работает
для любого поиска из журнала: с блоком `spec` (строка на позицию), с блоком `kit` (строка на слот, количество — число мест),
иначе — первые десять карточек с запрошенным количеством. Лист «Коммерческое предложение»: клиент (профиль), дата, срок
действия расчёта; таблица — №, запрос клиента, найденный товар, артикул, вендор, условия лицензии, количество, цена, сумма,
реестр российского ПО, примечание (замена, уточнение, «цена по запросу»); итог. Лист «Не найдено» — позиции без товара
и что предложено взамен. Внизу строка: расчёт предварительный, цены демонстрационные.

## 27.7 Консоль: готовые строки от API (отдаёт B, рисует C)

- Пара показателей в `GET /api/admin/kpi` получает необязательные поля: `tone` (`good`, `bad`, `neutral` — цвет изменения),
  `delta_text` («−22,1 п. п.», «−42,1 млн ₽»), `scope_text` (на каких данных посчитано). Общее пояснение ко всем плиткам —
  один раз, в поле `note` верхнего уровня ответа; у плитки `note` только своё, короткое.
- Пара `exit_after_fail` меняет смысл: доля поисков периода, после которых покупатель ушёл, не найдя нужного, **от всех
  поисков** (а не от неудачных); `n_before` и `n_after` — число таких уходов.
- У каждого предложения агента — готовые строки `evidence_text` (на чём основано: «312 поисков в 204 сессиях за 30 дней»,
  «14 клиентов с лицензиями до 20.01.2027») и `impact_text` (эффект). `confidence` может быть `null` — тогда интерфейс
  строку уверенности не показывает.
- `GET /api/admin/ingest`: `catalog` — содержимое `import_report.json` последнего импорта (включая раздел `ai`), `history` —
  отчёты импорта истории и Метрики, `review` — до 50 решений раскладки с низкой уверенностью из `import_ai.jsonl`.
- `GET /api/admin/ui/search-reference`: у каждой строки обычного поиска есть `card_id` — сравнение режимов идёт по карточке.
- `GET /api/admin/digest?role=<…>&format=json|md|xlsx` — отчёт для роли одним файлом (`md` и `xlsx` отдаются с заголовком
  `Content-Disposition`); в консоли — кнопка «Скачать отчёт».

## 27.8 Виджет для чужого сайта и голосовой ввод (делает C; A — разбор и CORS)

- Страница `/embed` — условная страница стороннего магазина с нашим поиском, подключённым одной строкой:
  `<script src="/web/embed/widget.js" data-profile="guest" data-mode="smart"></script>`. Виджет без зависимостей: строка
  поиска, подсказки (`/api/suggest`), выдача с «Понято так» и ценой (`/api/search`), события (`/api/event`).
- Для другого домена поток A добавляет переменную `KZ_CORS_ORIGINS` (список через запятую; пусто — заголовков нет).
- Голосовой ввод: кнопка‑микрофон на витрине и в виджете (Web Speech API, `ru-RU`); браузер не умеет — кнопки нет.
  Распознанный текст уходит в обычный поиск. Поток A разбирает числа словами («на тридцать компьютеров»).
