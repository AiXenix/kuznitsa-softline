# C2a · Доводка витрины по итогам просмотра в браузере

C1 принят и закоммичен (`1ca441e`), стенд открыт наружу. Я просмотрел витрину в headless Chrome (1366 × 900, 1366 × 1700,
360 × 1500): всё работает, ошибок в консоли нет. Ниже — что нужно довести. Оценка хакатона — «по демо», поэтому главный
критерий хода: **на проекторе 1366 × 768 понятный и плотный экран, на котором результат и разбор запроса видны сразу, без
прокрутки**.

**Что изменилось в твоей копии.** Все три потока слиты в `main`, твоя ветка `ui` подтянута к общей точке `c014d60`:
в копии теперь движок M2a (все 20 сценариев, новые цены и расчёт, цепочки запросов, сопутствующие товары), аналитика B1
(`kuznitsa/analytics/**`, служебный API `/api/admin/*`) и база знаний второго хода. 106 тестов проходят. В `var/data`
лежит снимок данных стенда: каталог (23 537 SKU, 660 карточек), клиенты, журнал с историей 45 000 поисков, парным прогоном
и 129 предложениями агента — служебный API отвечает настоящими данными. Свежие образцы ответов движка —
`docs/api_examples/*.json` (20 файлов, все 15 видов блоков; обрати внимание на `calc.qty = null`, `calc.items` для набора
пакетов, `calc.unit_price = null`), контракт консоли — `docs/ADMIN_API.md` и `docs/admin_examples/*.json`.
Первым делом прогони витрину на новых образцах: блоки и расчёт цены не должны ломаться на новых формах ответа.

Правила те же, что в C1: зона записи `web/**`, `kuznitsa/pages.py`, `tests/web/**`, `docs/UI.md`, `design/proposals/ui/**`;
без коммитов, без внешних шрифтов, CDN и сборщиков; числа — только из API. Содержание выдачи (названия, цены, выбор сценария)
— зона потока A; вёрстка должна выдерживать и длинные названия, и короткие. Если увидишь ошибку в данных ответа — не чини
на стороне витрины, запиши в отчёт.

Этот ход — C2a (витрина). Следующим сообщением в очереди придёт C2b (консоль `/admin` и разбор `/inspect`): начинай его
сразу после C2a, не дожидаясь меня.

Проверка глазами. На этой машине доступен `bb browser-automation` (headless Chrome): `bb browser-automation open --backend local
--headless --machine khaki-gazelle-91012 --json`, затем `run <id> --script '…' --json` (API как у Puppeteer: `browser.getPage("main")`,
`p.setViewport`, `p.goto`, `p.type`, `p.click`, `p.evaluate`, `await p.shot({type:"jpeg",maxEdge:1366,quality:50})`), снимок лежит по пути
из ответа. Если инструмент тебе доступен — подними свою копию на `127.0.0.1:8197` (`python -m kuznitsa.cli serve --host 127.0.0.1
--port 8197` из корня клона), посмотри снимки на ширинах 1366 и 360, после работы останови сервер и закрой сеанс (`close`).
Если недоступен — не трать время, я посмотрю сам.

## 1. Каркас и строка поиска (P0)

1. Кнопка «Найти» переносится на две строки («Найт / и») на любой ширине. Запретить перенос, задать минимальную ширину.
2. Шапка‑герой занимает ~470 px, после поиска выдача уходит за край экрана. После первого поиска (и при открытии по ссылке с
   запросом) герой сворачивается в плотную панель: одна строка — поле и кнопка, вторая — профиль, категория, режим в один ряд
   без крупного заголовка. Панель прилипает к верху при прокрутке. На 1366 × 768 после поиска должны быть видны без прокрутки:
   «Понято так», первая карточка с ценой и начало трассы.
3. Состояние в адресе: `/?q=…&profile=…&mode=…&category=…` (и признак режима сравнения). Поиск делает `history.pushState`,
   страница восстанавливается по адресу при загрузке и по кнопкам «назад/вперёд». Галерея сценариев и «Режим показа» открывают
   витрину такими ссылками. Сейчас после поиска адрес остаётся `/`.
4. «Понято так»: сейчас одно и то же написано дважды — фразой и чипами. Оставить заголовок, название сценария (крупно, например
   «Продление лицензии») и чипы. Чип профиля — короткий («Профиль: ТД «Вектор»» — часть названия до тире), полное описание — в
   подсказке `title`. Длинное название профиля сейчас повторяется на экране четыре раза.
5. Клавиши: `/` — фокус в поле поиска, `Esc` — закрыть подсказки/диалог.
6. Подсказки: подсветить совпавшую часть, справа у строки — тип («продукт», «вендор», «категория», «запрос», «ваша лицензия»).

## 2. Карточка товара (P0)

Сейчас карточка — высокая колонка (~440 px), на экране помещается одна‑две. Нужна плотная строка‑карточка (~150–190 px):

- слева номер позиции (1, 2, 3…) и плитка‑монограмма вендора (2 буквы на цветном фоне; цвет выводится из названия вендора;
  чужие логотипы не используем);
- в середине: строка «вендор / категория», название (до двух строк), описание (обрезка до двух строк), значки;
- справа блок цены: выбранный вариант лицензии одной строкой, расчёт крупно («30 × 1 883 ₽ = 56 490 ₽» либо «от 1 883 ₽ за
  устройство в год»), кнопка действия. «Цена по запросу» — отдельное оформление и кнопка «Запросить цену»;
- «Лицензия и варианты» и «Почему здесь» раскрываются под карточкой на всю ширину;
- значки двух видов: спокойные («В реестре ПО», «Без НДС», «У вас куплено», «Для учебных заведений») и предупреждающие
  («Поставки ограничены», «Вендор ушёл с рынка», «Больше предела линейки»).

«Лицензия и варианты»: вместо списка строк — таблица «Действие · Количество · Срок · Для кого · Поставка · Артикул · Цена»,
выбранная строка выделена; если полей в ответе нет — столбец скрывается, а не показывает прочерки.

«Почему здесь»: вместо «0,275 / 0,03169 / 0,13689 / 0» — четыре горизонтальные полосы (релевантность, популярность, маржа,
персонализация) с процентами и подписью веса, уровень релевантности словами (подпись из ответа, если есть, иначе «Уровень 2»),
причины списком. Точные числа — в `title`.

## 7. Страница «О решении» (P1)

Сейчас три абзаца — для жюри мало. Нужны разделы (текст ниже можно править стилистически, факты не менять):

- **Кому помогает.** Клиент — находит нужную лицензию с первого запроса. Менеджер e‑com — видит, где поиск теряет заказ, и
  управляет выдачей правилами. Продукт‑менеджер — видит, что ищут клиенты и как меняется спрос. Контент‑менеджер — видит, каких
  товаров и каких полей в карточках не хватает. Руководитель e‑com — видит эффект в заказах и деньгах.
- **Что происходит с запросом.** 15 шагов из трассы одной лентой (названия — те же, что в панели): нормализация → точный артикул →
  проверка написания → сущности и параметры → контекст клиента → сценарий запроса → план поиска → отбор кандидатов → проверка
  ограничений → выбор лицензии → проверка категоризатором → порядок карточек → правила магазина → сборка ответа → журнал и стоимость.
  У каждого шага одна фраза «что делает».
- **Какие запросы понимает.** Группы сценариев и число сценариев в каждой — из `/api/meta`, со ссылкой на галерею.
- **Почему поиск не выдумывает.** Категоризатор Jev выбирает только из закрытого списка вариантов, которые ему передал движок:
  сценарий, категорию, готовый ответ, оценку кандидата. Товаров, цен и условий он не сочиняет — всё берётся из каталога. Если
  внешний сервис недоступен или исчерпан дневной предел расходов, поиск продолжает работать в быстром режиме, это видно в трассе.
- **Порядок выдачи.** Сначала уровень релевантности (четыре полосы), внутри полосы — популярность, маржа и профиль клиента с весами
  из настроек; карточка из нижней полосы не может обогнать карточку из верхней.
- **Модели и библиотеки** — таблица «название · зачем · лицензия»: FastAPI и Uvicorn (веб‑сервис; MIT, BSD), pydantic (схемы; MIT),
  NumPy и SciPy (векторы; BSD), scikit‑learn (текстовые признаки; BSD), RapidFuzz (близкие написания; MIT), pymorphy3 (морфология
  русского языка; MIT), fastembed и ONNX Runtime (локальная модель; Apache 2.0, MIT), paraphrase‑multilingual‑MiniLM‑L12‑v2
  (смысловая близость; Apache 2.0), SQLite (журнал; общественное достояние), Jev 1.13 через OpenRouter (категоризатор; внешний
  платный сервис). Состояние внешней модели — из `/health`.
- **Стоимость запроса.** Только из API (`/api/admin/cost`): пока вызовов модели в журнале нет, API отдаёт нули — в этом
  случае показывай «ожидаются данные», а не «0 ₽». Качество на проверочном наборе — из `/api/admin/eval` по тому же правилу.
- **Данные стенда.** Каталог, цены, клиенты и журнал запросов синтетические; настоящие данные организаторов загружаются
  адаптером без изменения движка.
