## Задача хода C1

Движок сейчас умеет меньше, чем описано в разделе 17: поток A доделывает сценарии в этом же ходе. Поэтому рисуй по разделам
17 и 25.3, а не по тому, что движок отдаёт сегодня; на каждый вид блока сделай образец ответа в `web/fixtures/` и
терпимый к отсутствию полей отрисовщик (нет поля — элемент просто не показывается, неизвестный вид блока — аккуратная
карточка «блок не поддержан», ничего не падает).

### 1. Основа
Свои переменные оформления, типографика на системных шрифтах, светлая тема, состояния загрузки, пустоты и ошибки, работа с
клавиатуры, ширина от 360 пикселей. Модули: обращение к API, состояние, отрисовщики блоков, подсказки, трасса, события.

### 2. Витрина `/`
- Шапка: строка поиска; переключатель профиля клиента (гость и показательные профили из `/api/meta`, с карточкой «кто это»:
  сегмент, размер, что уже куплено, что истекает); контекст категории; режим «Умный / Быстрый / Наивный».
- Подсказки при вводе по группам (запросы, товары, категории, вендоры, «мои лицензии», ответы), с пометкой исправленной
  опечатки, полностью с клавиатуры.
- Над выдачей: «Понято так» — плашки условий; крестик снимает условие (повтор запроса с `ignore`); исправление запроса со
  ссылкой «искать как было» (`verbatim`); унаследованный контекст цепочки со ссылкой «начать заново» (`context: off`);
  баннеры; подсказки снятия одного условия; похожие запросы.
- Блоки всех видов: `products`, `kit`, `analogs`, `answer`, `spec`, `compare`, `not_in_catalog`, `categories`, `vendors`,
  `my_licenses`, `clarify`, `services`, `promo`, `lead`, `crosssell`.
- Карточка товара: название, вендор, признаки (реестр российского ПО, сертификаты, «цена по запросу»), вариант лицензии и
  расчёт (`calc`: «30 × 1 883 ₽ = 56 490 ₽» либо «от … за устройство в год», если количества нет), другие варианты,
  «Почему здесь» — уровень релевантности и вклад релевантности, популярности, маржи и персонализации.
- Фасеты; корзина‑заглушка (боковая панель, «Оформить заказ» завершает показ). Клики, добавления, заказы и уход без клика
  отправляются в `/api/event` — на них построена аналитика.
- Панель «Как работал поиск»: 15 шагов трассы со статусом, временем и подробностями, итоговое время, число обращений к модели
  и стоимость запроса. Это главный экран показа — он должен читаться с проектора.

### 3. Особые режимы
- «Вставить спецификацию»: многострочный список закупки → блок `spec` (что найдено, что нет, итог).
- Сравнение профилей: один запрос в двух‑трёх колонках под разными профилями (`source: compare`) — наглядно показывает
  «один и тот же запрос от разных людей даёт разную выдачу».
- Сравнение режимов: тот же запрос «наивный поиск» против «умного» в двух колонках.

### 4. Остальные страницы
- `/scenarios` — галерея 118 сценариев из `/api/meta`: группы, поиск по галерее, по нажатию пример запускается под своим
  профилем.
- `/inspect/{search_id}` — разбор одного запроса из журнала (`GET /api/admin/search/{id}`, его делает поток B; нет ответа —
  понятное сообщение).
- `/about` — как устроено решение, модели и библиотеки, стоимость запроса. Числа — только из API; где их ещё нет, оставь
  явную метку `data-pending`.
- `/styleguide` — все виды блоков и состояний из `web/fixtures/` на одной странице: по ней я проверяю вёрстку одним взглядом.

### 5. Подключение и проверки
- `kuznitsa/pages.py`: `router` со страницами и статикой (25.2). HTML без кэша, статика с `ETag`.
- `tests/web/`: страницы отдаются, образцы блоков разбираются и содержат поля, которые читают отрисовщики,
  `node --check` для каждого файла JavaScript.
- `docs/UI.md`: карта страниц, для каждого вида блока — какие поля читает интерфейс, допущения там, где раздел 17 молчит,
  как добавить новый блок.

Консоль аналитики `/admin` — следующий ход, когда поток B отдаст служебный API; сейчас только пункт меню и заглушка‑страница.
