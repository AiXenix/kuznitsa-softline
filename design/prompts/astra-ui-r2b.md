# C2b · Консоль бизнеса `/admin` и разбор запроса `/inspect`

Выполняется сразу после C2a в той же копии и по тем же правилам (зона записи `web/**`, `kuznitsa/pages.py`, `tests/web/**`,
`docs/UI.md`, `design/proposals/ui/**`; без коммитов; без внешних шрифтов, CDN, сборщиков и графических библиотек — графики
рисуются встроенным SVG; числа — только из API).

## Зачем

В условиях хакатона сказано: агент работает на пять ролей и «отдаёт не только выдачу покупателю, но и вывод для бизнеса».
Покупателя закрывает витрина. Остальные четыре роли закрывает консоль — это половина оценки. Жюри должно за 2–3 минуты
увидеть: (1) насколько поиск лучше прежнего и сколько это в заказах; (2) что агент сам нашёл в журнале и предложил;
(3) что предложение применяется одной кнопкой и эффект тут же проверяется; (4) что каждой роли — свой экран с её вопросами.

Источник данных — служебный API потока B: контракт `docs/ADMIN_API.md`, настоящие ответы `docs/admin_examples/*.json`,
живой API в твоей копии (журнал с историей уже лежит в `var/data`). Сценарий показа, под который делается консоль, —
`docs/DEMO.md` (шаги 5–9 варианта на 5 минут и весь вариант на 10 минут).

Поток B параллельно делает ход B2 и **добавит** поля (ниже помечены «B2»). Правило: если поле есть — показываем его, если нет —
работаем на том, что есть в B1, без заглушек с выдуманными числами. Ничего из B1 не удаляется.

## Каркас

- `/admin` — одна страница, вкладки переключаются без перезагрузки, вкладка и её параметры живут в адресе (`/admin#head`,
  `#ecom`, `#product`, `#content`, `#agent`, `#log`); ссылки на вкладки можно давать из «Режима показа».
- Шапка консоли: название, период данных и состав журнала (из `/ingest` и `/kpi`), пометка «данные синтетические»,
  поле «Ключ доступа» (хранится в `sessionStorage`, уходит заголовком `X-Admin-Token`). Чтение открыто без ключа; кнопки,
  меняющие данные, без ключа показывают подсказку «Нужен ключ доступа», а ответ 403 — понятное сообщение, не «ошибка».
- Плотная вёрстка под 1366 × 768: первая строка каждой вкладки — главный вывод роли, читаемый с последнего ряда.
- Единые форматы: `1 234 567 ₽`, `12,3 млн ₽`, `15,2 %`, даты по Москве. Пустое состояние у каждого блока («данных нет» +
  что сделать), состояние загрузки, сообщение об ошибке API с кодом.
- Любая фраза запроса в любой таблице — ссылка: клик открывает разбор `/inspect/{search_id}`, значок рядом открывает витрину
  с этим запросом (`/?q=…`).

## Вкладки

### 1. Руководитель e‑com — `#head` (вопрос роли: «сколько заказов мы теряем и что вернёт поиск»)

- **До / после** — главный блок: пары показателей «прежний поиск → Кузница» из `kpi.comparison` и последнего прогона
  `GET /replay/{run_id}`: доля пустых выдач, цель в первой пятёрке, число «возвращённых» поисков. Две полосы на показатель,
  разница крупно («−60,2 п. п.»). Если B2 отдаёт `kpi.pairs` (`[{key,label,unit,before,after,better}]`) — строим по нему.
  Подпись мелко: на какой выборке считано (число фраз и поисков) и что это парный прогон на одной истории.
- **Потерянные заказы** — `kpi.lost_orders`: осторожная и базовая оценка в рублях, сколько из неё приходится на сессии, где
  Кузница восстановила выдачу; раскрывающаяся «формула» из ответа. Никаких сумм, сложенных на стороне интерфейса.
- **Плитки** `kpi.tiles` и ряд по дням `kpi.slices.day` (линии: поиски, доля пустых; встроенный SVG, подписи осей).
- **Рычаг прибыли** — `GET /weights`, четыре ползунка с суммой 1 (при движении одного остальные пересчитываются
  пропорционально), кнопка «Предпросмотр» → `POST /preview`: сколько позиций сдвинулось, изменение маржи, **«Инверсий полос: N»**
  крупно; список «было → стало» для запроса из поля (по умолчанию — из топа). «Сохранить» → `POST /weights` (нужен ключ).
- **Экономика ИИ** — `GET /cost?daily=…`: стоимость запроса по режимам, доля ответов из кэша, прогноз на месяц при заданной
  нагрузке (поле ввода «запросов в сутки»), курс из ответа. Пока вызовов нет — «ожидаются данные».
- **Качество на проверочном наборе** — `GET /eval`.

### 2. Менеджер e‑com — `#ecom` («где поиск теряет заказ и чем я могу управлять»)

- Воронка поиска из `kpi.totals`: поиски → с кликом → в корзину → заказ; CTR первых трёх, средняя позиция клика, доля
  переформулировок, уходы после неудачи.
- Таблицы `GET /queries?kind=low_ctr | reformulated | zero` с переключателем.
- Причины неудач `GET /failures` — горизонтальные полосы с примером запроса.
- Предложения агента для роли: `GET /insights?role=ecom_manager` (горячие лиды, продления, правила выдачи) — те же карточки,
  что на вкладке «Агент».
- **Правила выдачи**: `GET /rules`, форма создания (`kind`: synonym, redirect, pin, ban, boost, bury, banner; условия
  `phrase | pattern | intent | category | segment | start | end`), включение/выключение, удаление. Для правила с фразой —
  кнопка «Проверить на запросе»: открывает витрину с этой фразой в новой вкладке.

### 3. Продукт‑менеджер — `#product` («что ищут клиенты и как меняется спрос»)

- «Пульс спроса»: `queries?kind=top` и `kind=rising` (текущее и предыдущее окно, прирост).
- Срезы `kpi.slices`: по сценариям (`intent`), категориям (первые 15 + «ещё»), сегментам клиентов — поиски, доля пустых,
  конверсия; сортировка по столбцу.
- «Импортозамещение»: `gaps.departed` (спрос на ушедших вендоров) и воронка замен `gaps.bridge` (показы → клики → корзины).
- Предложения агента для роли: `insights?role=product_manager`.

### 4. Контент‑менеджер — `#content` («каких товаров и каких данных не хватает»)

- «Пробелы ассортимента»: `gaps.items` — кластер спроса, вендор/категория, поиски, изменение к прошлому периоду, сегменты,
  оценка потерь; разрезы `gaps.breakdown` (по вендорам и категориям).
- «Дефекты карточек»: `gaps.card_defects` — карточка, каких полей нет, сколько показов; ссылка на карточку на витрине.
- «Словарь»: предложения `add_synonym`, `add_product`, `fix_card` (`insights?role=content_manager`).

### 5. Агент — `#agent` (вся лента предложений)

- Фильтры: роль, вид (восемь видов), статус (`new`, `applied`, `verified`, `rejected`), сортировка по оценке эффекта.
  Счётчики по видам сверху. Кнопка «Найти новые» → `POST /insights/refresh`.
- Карточка предложения: заголовок, роль, приоритет, уверенность (полоса; в подсказке — как считается), сводка,
  **доказательства** (примеры фраз — ссылки на разбор; число поисков и сессий; сегменты; чем заменяли запрос),
  **действие** (что именно будет сделано: правило, заявка, список клиентов, веса — человеческим языком из `action`),
  **эффект** (`impact`: осторожная и ожидаемая оценка, подпись метрики, пояснение формулы из ответа).
- Кнопки: «Применить» → `POST /insights/{id}/apply`; «Проверить» → `POST /insights/{id}/verify`; «Отклонить» →
  `POST /insights/{id}/reject`. После проверки — блок **«Было → стало»** по каждой фразе из ответа: число карточек,
  первые позиции, ссылки на обе трассы; ухудшения показываются так же честно, как улучшения. Статус меняется на глазах:
  `new → applied → verified`. Это ключевой кадр показа — «агент предложил, человек нажал, эффект измерен».
- Адрес карточки: `/admin#agent?id=…` (для «Режима показа»).

### 6. Журнал — `#log`

- Последние поиски витрины: если B2 отдаёт `GET /queries?kind=recent` — по нему (время, запрос, профиль/сегмент, режим,
  сценарий, число карточек, время ответа, стоимость); до тех пор — блок с пояснением и таблица `kind=top`.
- Состав журнала по источникам — `GET /ingest`.

## Разбор запроса `/inspect/{search_id}`

`GET /api/admin/search/{search_id}`. Страница для вопроса жюри «покажите, что происходит с запросом по шагам»:

- шапка: запрос, время, профиль/сегмент, режим, сценарий, число карточек, время ответа, вызовы модели, стоимость;
- слева — все 15 шагов трассы, каждый раскрыт: что получил, что решил, сколько занял (те же названия шагов, что на
  витрине; шаги с моделью, из кэша, пропущенные и «запасной путь» оформлены как в панели трассы);
- справа — сохранённая выдача теми же компонентами, что на витрине (без кнопок покупки);
- для импортированных и старых записей (`archived_summary = true`) — сводка и кнопка «Повторить запрос сейчас»
  (открывает витрину с этой фразой);
- кнопки «Открыть на витрине» и «Сравнить с наивным поиском» (витрина в режиме сравнения режимов).

Ссылка «Открыть разбор запроса →» из панели трассы витрины ведёт сюда.

## Режим показа

Шаги `web/demo/steps.json`, которые в C2a указывали на консоль, теперь ведут на конкретные вкладки и карточки
(`/admin#head`, `/admin#agent?type=add_synonym`, …). Идентификаторы предложений в шагах не зашиваются — они берутся
из API по виду и статусу (например, «первое предложение add_synonym со статусом new»).

## Приёмка

- `pytest -q` проходит; новые проверки в `tests/web/`: страницы `/admin` и `/inspect/{id}` отдаются; каждый адрес API,
  который запрашивает консоль, существует в приложении (сверка со списком маршрутов FastAPI); числа не зашиты в разметку.
- Проверь на снимке данных из `var/data` и (в тестах) на образцах `docs/admin_examples/*.json`: ни одна вкладка не падает
  на пустых списках, `null` и нулевых знаменателях.
- Действия с записью (применить, проверить, отклонить, правило, веса) проверь локально с ключом: запусти копию с
  `KZ_ADMIN_TOKEN=<любое значение>` на `127.0.0.1:8197`. Боевой ключ тебе не нужен.
- `docs/UI.md` дополнен; отчёт — `design/proposals/ui/REPORT-C2b.md`: что сделано; каких полей API не хватило
  (список для потока B); что показалось неправдоподобным в самих данных (для потока B — он в B2 калибрует историю).
