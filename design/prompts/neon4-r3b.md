# K2b · Поиск по профессиям, отраслям и ситуациям

Первый заход принят: ссылки в трёх твоих файлах базы знаний проверены скриптом — несуществующих семейств, категорий и
вендоров нет. Файлы зафиксированы в ветке `kb`. Спасибо за список сомнительных пунктов — он пойдёт на проверку человеку.

Правила прежние: терминал не используется; существующие файлы не изменяются; создаются только новые файлы из списка ниже;
`eval/queries.holdout.jsonl` не читается. В той же копии работает второй помощник — его файлы (`kb/slang_r3.yaml`,
`kb/families/absent_r3.yaml`, `kb/vendors_r3.yaml`, `kb/analogs_r3.yaml`) не трогай и не ссылайся на них.

## Зачем

Сильная сторона решения — поиск не только по названию, но и «от человека»: покупатель называет профессию, отрасль или
ситуацию, а магазин собирает комплект. Сейчас в базе знаний 46 ролей, 28 отраслей и 52 правила сопутствующих товаров.
Этого мало: первый же запрос жюри вроде «софт для сметчика» или «что нужно стоматологии» должен попасть в запись.

Источники идентификаторов — только таблицы `design/work/kb_families_r3.tsv`, `design/work/kb_categories_r3.tsv`,
`design/work/kb_vendors_r3.tsv`. Формат каждой записи — в точности как в базовом файле той же группы (`kb/roles.yaml`,
`kb/industries.yaml`, `kb/crosssell.yaml`, описание — `kb/SCHEMA.md`): тот же набор ключей в том же порядке, каждый ключ
присутствует, даже если значение пустое. Перед началом прочитай три базовых файла целиком.

  клиника; подготовка к проверке лицензий. У них `title` — название ситуации («Новый филиал: рабочие места и связь»).

Требования к записи:

- `aliases` — 8–12 формулировок так, как пишут в строку поиска: «софт для сметчика», «программы сметчику», «рабочее место
  сметчика», «что поставить сметчику», разговорные и сокращённые («сметчик по», «смета программы»). Без повторов чужих
  синонимов: один синоним — одна запись во всей базе (сверься с `kb/roles.yaml` и `kb/industries.yaml`).
- `slots` — 4–8 позиций. В каждой: `category` — листовая категория; `must: true` у 2–4 позиций, без которых рабочее место
  не работает; `families` — 2–5 семейств по убыванию уместности, сначала с `catalog: yes`; где есть российский вариант из
  реестра — он входит в список; `note` — одно предложение для покупателя: зачем эта позиция именно этой роли. Без
  рекламных слов и без выдуманных свойств продуктов. Поле `products` — как в базовом файле.
- Комплект собирается из того, что магазин продаёт. Если нужной категории нет в таблице категорий — позиция не создаётся,
  а пробел записывается в заметки.

## Файл 3. `kb/crosssell_r3.yaml` — 60 новых правил «с этим берут»

Прочитай 52 базовых правила и добавь те связки, которых нет. Ориентиры: серверная ОС → клиентские лицензии доступа,
терминальный доступ, резервное копирование, защита серверов; 1С → сервер 1С, СУБД, информационно‑технологическое
сопровождение, криптопровайдер для отчётности, электронный документооборот; отечественная ОС → служба каталогов,
виртуальные рабочие места, резервное копирование, антивирус для Linux, офисный пакет, почта; виртуализация → резервное
копирование виртуальных машин, мониторинг; почтовый сервер → антиспам, архивирование, защита от утечек; ВКС → лицензии
комнат и запись; СУБД → средства администрирования и мониторинга; межсетевой экран → подписки, центр управления,
VPN‑клиент; защита конечных точек → центр управления, песочница, SIEM; офисный пакет → редактор PDF, распознавание
текста, переводчик, электронная подпись; САПР → просмотрщик, управление инженерными данными, библиотеки; средства
разработки → анализ кода, работа с базами данных; управление проектами → база знаний, служба поддержки; удалённый доступ →
многофакторная аутентификация, контроль привилегированных пользователей.

- `when` — по категории или по семействам; `suggest` — 2–4 предложения с `reason`: одно предложение, которое покупатель
  увидит рядом с товаром («Серверу 1С нужна СУБД: без неё не развернуть базу на 20 пользователей»).
- Только то, что действительно докупают вместе. Заменители и конкуренты сюда не идут — для них есть аналоги.

## Файл 4. `design/proposals/neon4/probes-kits-r3.jsonl` — 240 проверочных запросов

По ним я измерю, узнаёт ли поиск роль и отрасль. Одна строка — один объект:

```json
{"q": "прога для сметчика на 3 места", "kind": "role", "expect": "cost_estimator", "seen": false}
```

- `kind` — `role` или `industry`; `expect` — идентификатор записи (базовой или новой).
- По два запроса на каждую новую запись и по одному на каждую базовую.
- `seen: true` — формулировка дословно есть в `aliases`; `seen: false` — пересказ, которого в синонимах нет. Не меньше
  половины запросов — пересказы: с количеством мест, с опечаткой, разговорные («чо нужно в стоматологию», «бухгалтерше
  программы», «софт нашим конструкторам»).

## Файл 5. `docs/SEARCH-KINDS.md` — каталог видов поиска

Справочник для жюри и для страницы «О решении»: что умеет поиск, сгруппировано по двадцати видам запросов из `SPEC.md`
(раздел о намерениях). Источники примеров — `eval/queries.dev.jsonl` (поле `scenario`: в нём около сотни мелких
сценариев) и `docs/DEMO.md`. Вверху — сводная таблица: вид поиска, пример запроса, что делает система, блок выдачи.
Ниже — двадцать коротких разделов: что это; пять примеров запросов из набора; какие мелкие сценарии сюда входят; чем
полезно покупателю и какой вывод получает бизнес (кому из пяти ролей заказчика). Отдельным разделом — сквозные
возможности: опечатки, раскладка, транслитерация, сленг, подсказки, учёт клиента и сегмента, ранжирование по
релевантности, популярности и марже, разбор запроса по шагам, цена запроса. Объём — до 300 строк. Обещаний о том, чего
в `SPEC.md` нет, не давать; чисел качества не приводить.

## Самопроверка перед сдачей

Каждый идентификатор семейства, категории и вендора есть в таблицах; категории в `slots` и `suggest` — листовые; нет
повторов `id` и синонимов ни внутри новых файлов, ни с базовыми; YAML разбирается (отступы — два пробела, строки
с двоеточием или кавычками — в кавычках); в JSONL каждая строка — отдельный объект.
