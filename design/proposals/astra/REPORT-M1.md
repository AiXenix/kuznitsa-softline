# Отчёт M1 · Кузница Softline

Витрина проходит весь путь от запроса до предложения лицензии и записи в SQLite. На контрольной сборке получилось 16 836 предложений, 45 карточек, 200 клиентов и восемь демонстрационных профилей.

Для «каспер продление на 30 компов» у торговой компании первой вышла расширенная редакция Kaspersky Endpoint Security для бизнеса. Выбран артикул `KL-AE5ABBBEB28D`, продление на 12 месяцев для 25–49 устройств. Расчёт **30 × 1 883 ₽ = 56 490 ₽**. После перекладки клавиатуры результат тот же. Все цены синтетические.

## Проверка

Выполнено из корня проекта на предоставленном Python 3.12.

```bash
.venv/bin/python -m kuznitsa.cli kb-check
.venv/bin/python -m kuznitsa.cli build-mock
.venv/bin/python -m kuznitsa.cli build-index
.venv/bin/python -m kuznitsa.cli search "каспер продление на 30 компов" --profile smb_trade --mode fast --explain
.venv/bin/python -m pytest -q
.venv/bin/python -m scripts.check_m1
```

**38 тестов прошли**. Тесты используют собственную KB и подставной HTTP-транспорт Jev. В установленном Starlette конструктор TestClient выдаёт одно предупреждение о будущей смене транспорта. Новых зависимостей нет. ONNX Runtime при загрузке может сообщить, что идентификатор телеметрии хранится в памяти. Локальная модель загружается в офлайн-режиме.

Через TestClient проверены витрина и её статические ресурсы, health, meta, GET и POST поиска, карточка со всеми вариантами, профиль, подсказки и запись события с ответом 204. Отдельно проверены журнал под параллельными запросами, ошибки API и ограничение частоты. Для 40 разных запросов «антивирус на N пк» (N от 31 до 70) от профиля клиники время POST целиком составило **42,0 мс по медиане, 63,8 мс на p95, максимум 76,9 мс**. Это последовательный прогон в одном процессе с готовым каталогом.

## Решения и граница этапа

- Основные семь планов работают локально. Сценарий и исполняемый план разделены. Например, у запроса о продлении сохраняется `intent=renewal`, действие лицензии обязательно, а отбор идёт по вендору или семейству. Шаг `plan` поясняет такой переход. Оба режима используют локальный конвейер. Живой Jev, кэш его решений, предохранитель и реранк относятся к M2.
- Ограничения ослабляются при пустом результате. Каждое снятие отражено в примечаниях. Регуляторика, исключения, действие и аудитория покупателя остаются обязательными. Вариант с превышением бюджета возможен только с примечанием о снятом ценовом ограничении. Диапазон и количество упаковок видны в выбранном предложении.
- Контракт публичных маршрутов сохранён в объёме M1. Поле чипа `remove_q` содержит запрос после снятия распознанной фразы. Уточняющие чипы и фильтры по фасетам пока простые. Профиль и категория страницы уже влияют на поиск. Наследование между репликами, полноценный подбор комплектов и сравнение профилей на одном экране отложены до M2. Режим `naive`, исторический журнал, аналитика продаж и админка относятся к M3.
- Модули небольших планов объединены в `plans/base.py`. Реализация символьного индекса находится в `index/cache.py`, API — в `app.py`, отключённый клиент Jev — в `llm/jev.py`. Базовый dev-раннер лежит в `evaluation.py`; пишет по каждому запросу результат проверки в JSONL. Полная аналитика прогонов и сравнение версий отложены. Значения конфигурации читаются из окружения, файл с секретами приложению M1 не требуется.
- Налоговый статус выдаётся по полям демопредложения. Для семейств из запасного набора сертификаты и факт включения в реестр остаются неопределёнными. Жёсткий фильтр по ним может дать пустую выдачу. Плоский импорт и обогащение по названиям SKU остаются следующей работой с данными организаторов.
- Быстродействие измерено при 45 карточках с большим числом вариантов. Масштаб в десятки тысяч разных карточек и параллельная нагрузка через сетевой сервер требуют отдельного испытания. Витрина проверена на уровне HTTP и синтаксиса JavaScript; визуальная проверка в браузере в этот прогон не входила.

## Состояние KB и вопросы

На последней проверке в KB были 306 вендоров, 134 категории, 488 записей жаргона, 12 регуляторных понятий, 46 ролей, 28 отраслей и 216 задач. YAML разобран без синтаксических ошибок. В `kb/families/` ещё не было семейств. Проверка исходной KB показала 120 висячих ссылок, включая сленговые имена будущих семейств. Они не мешают сборке. Запасные семейства сериализуются отдельно в `var/data/mock_families.jsonl`. После роста KB достаточно повторить `build-mock`, `build-index` и открыть новый экземпляр движка.

Профиль торговой компании в `mock/spec/profiles.yaml` владеет Small Office Security на 15 устройств. Запасная линейка заканчивается на 25 устройствах, поэтому запрос на 30 мест выводит Endpoint Security. Привязка записей истории к конкретным SKU выполняется только при наличии подходящего предложения.

Файл `eval/queries.dev.jsonl` во время проверки ещё отсутствовал. Команда `eval` явно сообщила об этом и выполнила три проверки из собственного демонстрационного набора, все три прошли. Это отдельный результат от pytest. Файл holdout не запускался.

Для M2 остаётся продуктовый вопрос: нужно ли дополнительно предупреждать при переходе с Small Office Security на Endpoint Security, что доступность межпродуктового продления зависит от условий вендора? В M1 выбранный SKU и «почему здесь» показывают семейство предложения и совпадение вендора с историей. Проверки права на такой переход пока нет.
