### 25.2. Швы между потоками (интерфейсы заморожены)

**Рычаги бизнеса — `kuznitsa/controls.py` (поток A).** Движок получает объект в конструкторе (`Engine(..., controls=None)`,
`Engine.open(cfg, ..., controls=None)`); реализация по умолчанию ничего не меняет. Поток B пишет свою —
`kuznitsa/analytics/controls.py`, класс `RuleControls(journal)`.

```python
class Controls:
    def version(self) -> int: return 0            # растёт при любом изменении правил или весов; движок сверяет перед каждым поиском
    def synonyms(self) -> list[dict]: return []   # {"phrase": "…", "to": "…", "kind": "vendor|family|category|use_case|text", "rule_id": "…"}
    def weights(self) -> dict | None: return None # {"rel","pop","margin","pers"}; None — веса из конфигурации
    def redirect(self, ctx: dict) -> dict | None: return None   # {"category": id} | {"q": "…"} | {"intent": "…"} + "rule_id"
    def merch(self, ctx: dict, cards: list[dict]) -> dict:      # после бизнес‑ранжирования, до сборки ответа
        return {"cards": cards, "banners": [], "fired": []}
```

- `ctx` = `{"q_raw", "q_norm", "intent", "category_id", "segment", "profile_id", "mode"}`.
- `cards` — упорядоченные карточки основного блока `products` в том виде, в каком они уходят в ответ (`card_id`, `vendor`,
  `category`, `score.tier`, …). `merch` возвращает новый порядок (закрепление, подъём, опускание, скрытие). Движок перенумеровывает
  позиции, кладёт `banners` в ответ (`"banners": [{"text", "kind", "rule_id"}]`) и пишет шаг трассы `merch` по `fired`
  (`[{"rule_id", "kind", "card_id", "summary"}]`). Синонимы `kind != "text"` подмешиваются в лексикон как сущности, `text` —
  как замена фразы до разбора; сработавший синоним виден в шаге `entities`. Порядок приоритета весов: `weights` запроса →
  `controls.weights()` → конфигурация.
- Гарантия ярусов (12.1) действует и после `merch`: `boost`/`bury` работают внутри яруса; `pin` и `ban` — осознанное действие
  человека, они показаны в трассе и в «почему здесь» («закреплено правилом»).

**Наивный поиск — `kuznitsa/plans/naive.py` (поток A).** `match(catalog, q, limit=20) -> list[Offer]`: нижний регистр, разбиение по
пробелам, все слова входят подстрокой в название SKU, сортировка по популярности. `Request.mode` принимает `naive`: ответ в
обычном формате (блок `products`, карточка на каждое SKU без склейки, трасса из двух шагов, `engine = "naive"` в журнале).
Поток B использует `match` при генерации исторического журнала и в сравнении «до/после».

**Журнал — `kuznitsa/analytics/store.py` (с этого момента поток B).** Движок вызывает только `journal.search(ts, req, r, count,
reason, relaxed)` и `journal.event(ts, data)`; сигнатуры не меняются. Всё остальное журнал берёт из ответа `r`: стоимость — из
`r["cost"]` (`llm_calls`, `cached`, `usd`), предыдущий запрос цепочки — из `r["understood"]["inherited"]["from_search_id"]`,
причину нулевой выдачи — из `reason` (поток B вправе уточнить её своими правилами по трассе).
Таблицы `llm_calls` и `llm_cache` создаёт и пишет поток A (`kuznitsa/llm/`), в том же файле SQLite; поток B их только читает.
Таблица `kv` общая, DDL у обоих одинаковый: `CREATE TABLE IF NOT EXISTS kv(key TEXT PRIMARY KEY, value TEXT, updated REAL)`;
ключи потока A начинаются с `session:`, потока B — с `settings:` и `rules:`.

**Подключение к приложению (`kuznitsa/app.py`, поток A).** При создании приложения подключаются, если модуль существует:
`kuznitsa.api.admin` (объект `router`, все пути под `/api/admin`), `kuznitsa.pages` (объект `router`: страницы и статика),
`kuznitsa.analytics.controls` (`RuleControls(journal)` → в движок). Необязательные маршрутизаторы регистрируются **раньше**
встроенных маршрутов `/` и `/web`, чтобы страницы потока C их заменяли. Движок доступен обработчикам как `request.app.state.engine`.

### 25.3. Что нового в контракте API (к разделу 17)

- После этапа M2 поток A сохраняет настоящие ответы движка в `docs/api_examples/<сценарий>.json` (по одному на тип блока и

### 25.4. Витринные названия (к разделам 3, 5)

Поле `name` семейств в `kb/families/*.yaml` часто содержит версии, пояснения и перечни редакций в скобках
(«Astra Linux Special Edition (1.7 / 1.8)», «Кибер Бэкап (Cyber Backup)», «Postgres Pro (Standard / Enterprise / Certified)»).
На витрину оно в таком виде не выходит.

- Файл `kb/overrides/families.yaml` (пишет Neon), отображение `id семейства → поправки`:

```yaml
astra_linux_se:
  title: Astra Linux Special Edition          # витринное название: бренд + продукт, без версий, скобок и пояснений
  editions: {orel: «Орёл», voronezh: «Воронеж», smolensk: «Смоленск»}   # id редакции → название редакции без повтора семейства
  max_seats: null                              # необязательно (24.4), только достоверное
  upgrade_to: null                             # необязательно (24.4), id семейства
```

- Загрузчик накладывает поправки на семейства. Заголовок карточки = `title` + пробел + название редакции (если редакция есть).
  Общее правило: любой другой ключ поправки (`price_rub`, `registry`, `certs`, `market_status`, `popularity`, `catalog`, …)
  заменяет одноимённое поле семейства целиком — так исправляются факты без переписывания больших файлов.
- Если поправки нет, название чистится автоматически: хвостовые скобки убираются, их содержимое остаётся в поисковом тексте
  (как алиасы и версии); из названия редакции убирается повтор названия семейства; одинаковые слова подряд не повторяются.
- Исходные `name`, `aliases`, версии по‑прежнему участвуют в поиске. `kb-check` сообщает о поправках к несуществующим id.

### 25.5. Цены и расчёт в mock‑каталоге (к разделам 10.2, 19)

На витрине не должно быть нелепых сумм («1 пак. по 1 × …», «8 пак. по 2 × 289 710 ₽», «250 × 76 000 ₽ = 19 000 000 ₽» без
запроса количества, одинаковая цена у всех редакций).

**Что значит `price_rub` семейства.** `unit` — за что цена: `device_year`, `user_year`, `mailbox_year`, `core_year`,
`server_year`, `site_year` — одна единица метрики на 12 месяцев; `device`, `user`, `server`, `core`, `cpu`, `mailbox`, `storage` —
одна единица бессрочно; `pack_year` — **один пакет** на 12 месяцев; `other` — одна лицензия или установка в том виде, как она
продаётся. `low … high` — разброс по конфигурациям линейки при базовой аудитории, сроке 12 месяцев и действии `new`:
`low` — самая дешёвая (младшая редакция, самый крупный диапазон, наименьший пакет), `high` — самая дорогая, `typical` — ходовая.
Все цены семейства при этих условиях лежат в пределах `0.8·low … 1.2·high`.

**Правила генератора.**
- Редакции — возрастающие коэффициенты в порядке списка (младшая → старшая), размах подобран под `low … high`.
- Диапазоны количества — цена за единицу монотонно убывает (3–8 % на ступень).
- Пакеты — цена пакета растёт с размером, цена за место убывает. Пакет на одно место — обычная лицензия без слова «пакет».
- Лицензирование по ядрам с пакетами (Windows Server: базовый пакет на 16 ядер и дополнительные на 2): `price_rub` относится к
  базовому (самому большому) пакету, меньшие — пропорционально числу ядер с небольшой наценкой.
- Срок: 24 месяца ≈ ×1,8, 36 ≈ ×2,5 к 12 месяцам. Продление ≈ 60–75 % новой лицензии; докупка — по цене новой за единицу;
  апгрейд ≈ 50–70 %. Образовательная ≈ 30–50 %, для госучреждений ≈ 85–100 % коммерческой.
- Часть дорогих корпоративных конфигураций — «цена по запросу». Цены округлены «по‑магазинному».
- Намеренные дефекты контента из `mock/spec/README.md` (для находок агента) сохраняются и помечены в скрытой разметке генератора.

**Расчёт `calc`.**
- Количество есть в запросе → расчёт на него. Диапазоны: «30 × 1 883 ₽ = 56 490 ₽». Пакеты: комбинация пакетов с минимальной
  суммой, покрывающая N: «2 пакета по 15 устройств × 21 900 ₽ = 43 800 ₽». Ядра: базовый пакет + дополнительные.
- Количества нет → **не подставлять выдуманное**: `calc.qty = null`, текст «от 1 883 ₽ за устройство в год» и условие
  («при покупке от 25»); для пакетов — «от 8 900 ₽ за пакет на 5 устройств».
- Продление своего продукта без количества → количество из купленной лицензии; это персонализация, она названа в «почему здесь».
- Комплект (`kit`): N из запроса, иначе `size_seats` профиля, иначе расчёт на одно место.
- Запрошенное больше `max_seats` линейки — раздел 24.4.

### 25.8. Проверочные запросы (к разделу 20)

- Ожидаемые названия (`top5_any`, `top1_any`, `must_not`, `family_any`, `vendor`, `exclude_vendor`) сначала сопоставляются с
  базой знаний через лексикон (название → id семейства или вендора) и сравниваются по id; подстрока заголовка — запасной способ.
- Если ожидаемого семейства нет в текущем каталоге (нет карточки), проверка получает статус `data_gap` и считается отдельно:
  итог печатается как «пройдено / не пройдено / нет в данных».
- `expect` — свободный текст для человека; машинные условия — только в `assert`.
- `eval/suggest.dev.jsonl` (пишет Neon‑2): `{"id", "prefix", "profile", "expect_any": ["…"], "group": "queries|products|categories|vendors|my|answers", "corrected": bool}`.
